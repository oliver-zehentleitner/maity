### Added

- hub: the gate of the agent firewall (§9.6, "Waiting"), part 2 of 3. An agent in a group chat with someone of another side its owner's entries do not cover waits: its participant item shows `waiting_for`, it is in no audience of the chat's events (`waiting:<id>`, which its owner reads along by), the chat is `not_found` for it and missing from its list and resume packet, a post answers `forbidden` (`waiting`), no mention, `chat_unread` or jour fixe step names or wakes it, and a round's view shows it no statement and no posts. Once admitted, its window starts at the admission. The owner's add is the yes (an allow entry for the agent and each side in the chat); a deny entry makes the add answer `forbidden` (`chat_denied`) and makes the agent leave when someone it names joins (`denied_participant`). Every change of an owner's entries settles that owner's chats again, and the worker lets the agents an ended allow entry admitted wait again. Every agent of another owner already in an open group chat waits after the migration `20261112100000_firewall_waiting`. Each change emits `conversation_updated` with `participants_changed`. A free work message (`notice`, `blocker`, `handover`, `interface_change`, `go_request`) from another side reaches an agent only when it is admitted for the author: otherwise the agent is held (`held:<id>` in place of its token, no role, trust or `all` token reaches it, no wake), its owner reads it along, and the event's payload names the held agents in `held` (`[]` when none, on every message). A lead (trust `owner` or `admin`, or a manager whose line the agent is in) is not gated; neither are cards, reviews and `update`. The point where a chat text may cross the owner boundary is in place on every path that stores one; it checks nothing yet. The request to the owner and the rules per side are part 3.
