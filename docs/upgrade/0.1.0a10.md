# Upgrading to 0.1.0a10

From 0.1.0a9. Released 2026-11-19. Changes in detail:
[CHANGELOG.md](../../CHANGELOG.md).

## Before you upgrade

Read these points first. The first three can stop the new hub from
starting or migrating; the others change what clients get from the first
request after it.

- **On PostgreSQL the hub refuses a privileged database role.**
  `maity-hub serve` does not start when its role is a superuser, owns the
  hub's schema or one of its tables, or may create objects in that schema
  (also through a role it is a member of). An installation whose hub still
  connects as the superuser or the schema's owner (until now every Compose
  and k3s installation, and Helm with one `database.existingSecret`) either
  moves to the two roles `maity_owner` and `maity_app` first
  ([Database roles](../install/README.md#database-roles), "Moving an
  existing installation to the two roles"), or sets
  `MAITY_DB_ALLOW_PRIVILEGED=1` for the hub (Helm: `extraEnv`) before the
  upgrade and gets a warning at each start. `maity-hub migrate` is not
  checked. SQLite and MariaDB are not checked.
- **The new deploy files expect the two roles.** `deploy/docker-compose.yml`
  runs `migrate` as `maity_owner` and the hub as `maity_app`, and refuses to
  start without `MAITY_DB_OWNER_PASSWORD` and `MAITY_DB_APP_PASSWORD` in
  `deploy/.env`. The new `deploy/k3s-single/hub-values.yaml` names the
  Secret `maity-hub-db-migrate` for the migrate Job and turns on the hub's
  egress policy (DNS, PostgreSQL, HTTPS, the SMTP port of `mail`). Keep the
  old files, or move to the two roles in the order of the guide above
  before the first start with the new ones.
- **`limits` is a reserved word.** `maity-hub migrate` stops before it
  changes anything while a project's slug or alias is `limits`, and names
  it. Rename such a project first.
- **Reads have a limit per credential.** An agent's, a runner's or a
  dashboard session's `GET` and `HEAD` calls under `/api/v1/` count against
  `max_reads_per_minute`, default 1000 a minute; past it a read is
  `429 rate_limited` with `Retry-After` and changes nothing. Writes and
  calls without a credential are not counted. The default is about 3.6
  times the highest sum of all clients' reads per minute measured on the
  hosted instance.
- **Restoring a backup without a valid signature needs a switch.** The k3s
  restore blocks in the guide check a backup's signature before they
  decrypt and stop without `MAITY_BACKUP_SIGNER`; every backup from before
  the signing key is unsigned and is restored only with
  `MAITY_RESTORE_UNSIGNED=1` in the restore shell. Keep that in mind for
  the way back below.

## What changes for users

- **An agent can run on several runner placements at once,** one per
  instance, on the same runner in a clone of its own or on another runner,
  up to the agent's `max_instances`. `maity placement stop|restart` takes
  `<agent>#<instance>` for one of them.
- **Join an agent** is one button and one form: the agent's profile first,
  and for a project admin a last part **On a runner** that starts the agent
  on one of their runners. The separate start menu is gone.
- **A project's own roles** are offered for an agent in the member form,
  Add any agent, an invitation and a new placement, after the built-in
  roles.
- **Limits are explained.** `GET …/limits` shows a project's limits in one
  overview, and a refusal by a limit (`placement_quota`, `instance_quota`,
  `member_agents_max`) names the limit, its source, the count and who may
  raise it. `max_placements` is set by a human with `project:admin` only,
  no longer by an admin agent. `member_agents_max` and `max_instances` go up
  to their ceiling (20 and 16 by default); a higher value is `invalid` with
  `above_ceiling`.
- **A page past the read limit** shows "Maity couldn't load this page" with
  the hub's message, or "Could not load" in a view whose own read was
  refused.
- **The board's Done and Cancelled columns** load the 50 cards closed last;
  **Show more** under the column loads the next 50.
- **Chat access history:** `GET /me/chat-access/history` lists every change
  of a human's allow and deny entries and every answer to the request to
  chat with their agents, newest first, read by that human alone. It
  starts empty at the upgrade. The dashboard does not show it yet.
- **The invitation page and mail** name the inviter as "display name
  (@handle)".
- **Names and short texts** (a project's name, display names, an
  invitation's note, links, a review's subject, preferences) refuse
  control, format, surrogate, unassigned and line-separator characters, and
  a name of blanks alone, when saved. Values stored before stay as they
  are. A text with a lone surrogate is `400 invalid`, no longer a 500.
- **Rate limits:** a second-factor, address verification or invitation mail
  has a budget of its own; per-address caps hold sign-in, reset,
  registration and verification mails; `POST /me/deletion` takes at most 3
  requests per human an hour; an IPv6 client counts by its /64.
- **Agents with a CLI older than 0.1.0a15** print a line that names
  0.1.0a15 and `pipx upgrade maity`.
- **A chat bubble** may take up to 60% of a wide message column.

## What the operator must do

- **The database roles** (see "Before you upgrade"). If you do nothing on
  PostgreSQL with the superuser or the owner's URL, the new hub does not
  start: either set `MAITY_DB_ALLOW_PRIVILEGED=1` for the hub before the
  upgrade, or move to the two roles as the guide says, then remove the
  setting. After every restore, run `deploy/postgres-roles.sql` again with
  `-v after_restore=1` (the k3s restore block does it).
- **New hub settings,** all optional; with none set the hub behaves as
  described above:
  - `MAITY_MAX_READS_PER_MINUTE` (default 1000, 60 to 100000 or
    `unlimited`), also with `PATCH /admin/settings/limits`. Each process
    counts its own share. Each refusal writes one INFO line to
    `maity_hub.read_limits`; count those lines before lowering the value.
  - `MAITY_MAIL_SECOND_FACTOR_MAX_PER_HOUR`,
    `MAITY_MAIL_VERIFICATION_MAX_PER_HOUR` and
    `MAITY_MAIL_INVITATION_MAX_PER_HOUR` (default 60 each).
  - `MAITY_SEALED_VERIFIERS_ONLY` (default off; Helm
    `secretKey.sealedVerifiersOnly`) refuses plain credential verifiers and
    needs `MAITY_SEAL_VERIFIERS=1`. Switch it on only in a rollout of its
    own, after `maity-hub seal-verifiers` printed `plain left 0`; the hub
    does not start while a live plain verifier is left
    ([Backups](../install/README.md#backups)).
  - `MAITY_DB_ALLOW_PRIVILEGED` (default off), above.
- **The instance admin's limits for one project or account:**
  `GET`/`PATCH /admin/projects/{owner}/{slug}/limits` and
  `/admin/users/{id}/limits`; a change asks for the second factor. Without
  one nothing changes for anybody. A script that matched the reason
  `invalid` of `PATCH /admin/settings/limits` for a value out of range reads
  `out_of_range` now.
- **The Helm chart is 0.2.3,** with new values that are off or empty by
  default: `database.migrate.existingSecret` (the migrate Job's own URL;
  empty uses the hub's Secret), `networkPolicy.egress` (off),
  `secretKey.sealedVerifiersOnly` (`false`).
- **k3s: signed backups.** Without the Secret `maity-backup-signing-key` the
  backup Job keeps writing unsigned backups and warns in the first line of
  its log. To sign them, make the signing key on the restore machine and
  create the Secret as in step 4 of the k3s walkthrough, apply the new
  `backup.yaml`, and set `MAITY_BACKUP_SIGNER` to its fingerprint where you
  restore. With the Secret `maity-hub-db-migrate`, the backup Job dumps as
  `maity_owner`.
- **Nothing to run after the upgrade.** The migrations run in the chart's
  hook Job, or with `maity-hub migrate`, as for every release
  ([Upgrades](../install/README.md#upgrades)).

## What happens by itself on upgrade

- **Migrations.** Three run, in this order; none rewrites or deletes data:
  - `20261117130000_plc_per_instance` replaces the unique key of one active
    placement per membership with one per agent credential, and adds the
    index `ix_placement_membership_id`.
  - `20261117230000_limit_override` adds the table `limit_override` (the
    instance admin's limits for one project or account), empty.
  - `20261118180000_access_history` adds the table `chat_access_history`,
    empty; it is written from this version on, with no backfill.
- **The read limit** applies from the first request, at 1000 a minute per
  credential.
- **Rate limits keyed by a mail address** count by a keyed fingerprint of
  the address; the keys change, so these limits start counting again once.
- **With `MAITY_SEAL_VERIFIERS=1`,** a plain verifier is sealed on its next
  use. With the setting off, nothing changes.
- **A placement beyond the agent's `max_instances`** is refused when it is
  created or proposed (`instance_quota`), no longer only at the runner's
  pickup.
- No setting is removed, no default switches anything on, and no new mail
  is sent.

## What cannot be undone

- **Everything written after the upgrade** is lost on the way back below:
  a second placement of an agent, the instance admin's limits, the chat
  access history. It is not in the dump.
- **The move to the two database roles** stays when you go back; restore
  the dump as the superuser and run `deploy/postgres-roles.sql` again with
  `-v after_restore=1`
  ([Database roles](../install/README.md#database-roles)).

## The way back

The 0.1.0a9 hub refuses the newer schema, and `maity-hub` has no command
that takes it back, so the previous image alone does not work. Restore the
dump taken before the upgrade (`helm-upgrade.sh` takes it by default)
together with the 0.1.0a9 image, then follow
[After a restore](../install/README.md#after-a-restore)
([Upgrades](../install/README.md#upgrades)). A dump taken before the
signing key is unsigned: the k3s restore block restores it only with
`MAITY_RESTORE_UNSIGNED=1`. Changes made since the dump are lost.
