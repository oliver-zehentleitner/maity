# Upgrading to 0.1.0a11

From 0.1.0a10. Released 2026-11-23. Changes in detail:
[CHANGELOG.md](../../CHANGELOG.md).

## Before you upgrade

Read these points first. The first one can stop the new hub from
starting; the second decides the order of two upgrades; the others change
what runners do once the hub is upgraded.

- **A mirrored Keep the Why skill needs its commit.** If you set
  `MAITY_KTW_SKILL_SOURCE`, also set `MAITY_KTW_SKILL_COMMIT` to the full
  git commit (40 hex digits) of that tree, for example from
  `git ls-remote <repository> refs/tags/<tag>^{}`. A hub with the source
  set and the commit unset, or a commit that is not 40 hex digits, refuses
  to start. With neither set, nothing is needed: the default source comes
  with its commit.
- **MariaDB 11.7 or newer: upgrade the hub first.** 0.1.0a10 and older use
  the column name `vector`, a reserved word from MariaDB 11.7 on: their
  `maity-hub migrate` fails on a new database there, and on an existing one
  storing a notification position fails. 0.1.0a11 quotes it. Upgrade the
  hub, then the MariaDB server
  ([Database versions](../install/README.md#database-versions)).
- **Runners start delivering the Keep the Why skill.** From this version
  the hub names the skill (`keep_the_why: {source, commit}`) on every
  placement of a project that uses Keep the Why. A runner with `maity`
  0.1.0a18 or later then fetches that commit with its own git over https
  (from github.com, unless you mirror it) and gives it to the agent's
  session. A runner that cannot reach the host starts the session without
  the skill and reports `keep_the_why_unavailable`; nothing is refused.
- **Runners start watching their placements.** From this version the
  hub's placement read carries each placement's `session`. A runner with
  `maity` 0.1.0a18 or later then watches placements whose session stopped
  listening (15 minutes) or never joined (10 minutes after the start), and
  reacts by cause: one restart that resumes the session, one nudge, a wait
  for a provider limit, or `failed`. Its settings are under
  `[limits.watch]` on the runner (`docs/runners.md`); `auto_restarts = 0`
  makes it hold the placement as failed instead of restarting.

## What changes for users

- **Stars:** a signed-in human keeps public projects they are not a
  member of as tabs (`PATCH /me` `starred`), at most 100 by default.
- **Outsiders read public projects:** a signed-in human who is not a
  member reads a public project's view, members, cards, a card's history
  and notes, logo and banner, and, in the operator's own namespaces, its
  Why view while the forge says the repository is public. Everything else
  answers `not_found`; a not-done `security` card and a card under a
  moderation hold stay hidden. Only with public pages on.
- **A member places their own agent** that is not in the project yet on a
  runner of their own, from **Join an agent**, **On a runner**, where the
  project lets members bring their own agents (`policy.member_agents`).
- **Reset** next to **Restart** on a managed agent: a restart on a fresh
  harness session (`maity placement restart --fresh-session`).
- **A placement names its reasoning effort** (`effort`) where the runner
  offers efforts for its harness (Codex, Antigravity).
- **A review answers the message that ordered it** (`maity say --type
  review_result --in-reply-to SEQ`), and the orderer is woken.
- **A project's links** take a **Docs** link, shown in the header when set.
- **Chat access history** is shown under Agents → Chat access.
- **A project's runners** are the **Runners** tab of its Settings; the old
  view `/<owner>/<slug>/runners` answers not found.
- **The join page** says when the new member will read the project's
  restricted texts.
- **A merged pull request closes a card by itself** (`merged_closes:
  auto`) only when it is that card's own; otherwise `task_merged` says
  `closed: false` with the reason, and the done authority closes the card.
- **A `review_result`** adds a boss through `reports_to` only when that
  boss has the same owner as the agent it leads.
- **An account deletion** also clears the person's links and switches off
  every public switch of the account.
- **Agents with a CLI older than 0.1.0a18** print a line that names
  0.1.0a18. Runners need that `maity` for the skill, the watch and
  `maity uuid`.
- **The dashboard** reads fully in Spanish, French, Italian, Japanese,
  Korean, Dutch, Portuguese and Simplified Chinese again, and the mails of
  a changed password and of second-factor codes refused for the day in
  those languages too.

## What the operator must do

- **`MAITY_KTW_SKILL_COMMIT`** (new; default: the commit of the default
  source's release tag): only if you set `MAITY_KTW_SKILL_SOURCE`, see
  "Before you upgrade". If you do nothing with the source set, the hub
  does not start.
- **`MAITY_MAX_STARRED_PER_HUMAN`** (new; 1 to 1000, no `unlimited`;
  unset leaves it to the instance admin, default 100), also under
  `PATCH /admin/settings/limits`. Lowering it keeps the stars a human
  holds. If you do nothing, every human may star 100 projects.
- **Runners:** update `maity` on each runner to 0.1.0a18 and restart its
  placements. Until then a runner neither delivers the skill nor watches,
  and placed Claude Code and opencode agents have no UUID source. Let the
  runner reach the skill's host (github.com by default) if its projects
  use Keep the Why.
- **The runner watch:** runners on `maity` 0.1.0a18+ restart quiet
  placements by default; set `[limits.watch] auto_restarts = 0` to only
  diagnose them. If you do nothing, the watch restarts a quiet placement
  once within its window.
- **The Helm chart is 0.2.4,** with no new value; only its `appVersion`
  changed.
- **Nothing to run after the upgrade.** The migrations run in the chart's
  hook Job, or with `maity-hub migrate`, as for every release
  ([Upgrades](../install/README.md#upgrades)).

## What happens by itself on upgrade

- **Migrations.** Six run, in this order; three add a column, two only
  add rows, and one moves columns into new tables:
  - `20261120090000_fresh_session` adds the nullable column
    `placement.fresh_session_generation`. Metadata only.
  - `20261118090000_starred` adds the nullable column `human.starred`.
    Metadata only.
  - `20261120205253_plc_agent_id` adds the nullable column
    `placement.agent_id`, an index and a foreign key on it, and widens the
    check `ck_placement_names_an_agent`. The index is built over every
    placement row; the check is validated over them.
  - `20261121120000_inst_attach` creates the tables `instance_attachment`
    and `agent_session_project`, copies every credential into one
    attachment and every agent session into one position row (two
    `INSERT … SELECT` and one `UPDATE`, whatever the number of rows), then
    drops the moved columns from `credential` and `agent_session` and adds
    `join_link.attach`. It rewrites `credential` and `agent_session`
    (dropping columns, adding an index and a foreign key); the time grows
    with those two tables. Data is moved, not lost.
  - `20261121130000_plc_effort` adds the nullable column
    `placement.effort`. Metadata only.
  - `20261123120000_acct_lock_rows` inserts the missing `account_lock`
    row of every human, in one statement.
  - `0034` itself is not run again: only the spelling of its DDL changed
    (the column `vector` is quoted).
- **The runner's placement read** carries `keep_the_why` and `session`:
  runners with `maity` 0.1.0a18 start delivering the skill and watching
  their placements (see "Before you upgrade").
- **The hourly registration pass** deletes registration blocks that have
  run out, with their address.
- **The hub names CLI 0.1.0a18** as the newest, so older agents print an
  upgrade line.
- **Credential ids and cookies** of a form the hub never issues are
  refused as unknown (`401`) instead of failing later.
- No setting is removed and no new mail is sent.

## What cannot be undone

- **Everything written after the upgrade** is lost on the way back below:
  stars, placement efforts and resets, placements of profiles that were
  not members yet, findings. It is not in the dump.
- **Skills a runner fetched** stay in its
  `~/.local/share/maity-runner/skills/`; they are plain files.
- **Restarts and nudges** the runner's watch made, and registration blocks
  the hourly pass deleted, stay.

## The way back

The 0.1.0a10 hub refuses the newer schema, and `maity-hub` has no command
that takes it back, so the previous image alone does not work. Restore the
dump taken before the upgrade (`helm-upgrade.sh` takes it by default)
together with the 0.1.0a10 image, then follow
[After a restore](../install/README.md#after-a-restore)
([Upgrades](../install/README.md#upgrades)). A dump taken before the
signing key is unsigned: the k3s restore block restores it only with
`MAITY_RESTORE_UNSIGNED=1`. Changes made since the dump are lost.
