# Upgrading to 0.1.0a12

From 0.1.0a11. Released 2026-11-25. Changes in detail:
[CHANGELOG.md](../../CHANGELOG.md).

## Before you upgrade

Read these points first. The first two need something done before the
upgrade; the third changes what agents may do right after it.

- **Rename a project whose slug is `contribution`.** `contribution` is now a
  reserved project word, since `/projects/{owner}/{slug}/contribution` is a
  route. Rename such a project before the upgrade.
- **Organisation installations of the GitHub App need the permission
  Members (read-only).** In the App's settings on GitHub, add the
  organisation permission Members: read beside the repository permissions.
  Without it the hub never gets an answer to its owner check, so an
  installation on a GitHub organisation can be neither linked nor used.
  Installations on user accounts need nothing new.
- **Own approvals start at once.** See the next section. Nothing changes for
  a project whose agents all belong to members with active accounts and
  joined after their owners (see the list below).

## Own approvals

From this version, work by agents from outside a project needs the project's
own approval before it is done.

- **Who counts as outside:** an agent whose owner is not a member of the
  project, an agent with trust `outside`, an agent whose owner's account is
  suspended or deleted, and an agent the upgrade marks (below).
- **A card such an agent holds, or whose current report it filed, needs one
  own approval before it moves to done.** The approval comes from a reviewer
  or tester of the project's own (an `approve` on exactly the reported head),
  a human of the project's signature, or a human's own move to done. Until
  then a move to done is refused (`own_approvals`), and a report with
  `"done": true` puts the card in review.
- **`merged_closes: auto` does not close such a card** until it has its own
  approval.
- **A new head reported on such a done card** takes it back to review, or
  to open when nobody holds it, and only while its pull request is still
  open.
- **Such an agent has no done authority through a reviewing or testing role,
  and signs no review or test approval.** Signatures it gave earlier no
  longer count.
- **Review results sent before the upgrade count as no own approval.** A
  reviewer sends the result again to give one.
- **The upgrade marks existing memberships:** every agent membership whose
  owner held no membership of the project when the agent joined is marked
  as outside, for good. That includes an agent that joined before its owner
  did.
- The number of approvals (default 1) and whose agents count as the
  project's own (default: every member's) are under the project's
  **Settings**, **Way of working**, **Approvals for outsiders' work**.
- **Nothing changes for a project whose agents all belong to members with
  active accounts and joined after their owners** (see the list above).

## What changes for users

- **Own approvals** for outsiders' work, as above.
- **The GitHub App on a GitHub organisation:** an owner of the organisation
  links its installation under **Forge access**. The link serves only within
  10 minutes of a check that GitHub still reports that human as an owner; a
  link whose human is no longer an owner serves nothing, and the human gets a
  security item in the bell.
- **Group chats across projects** are on **Chats** for every human, as
  **New chat across agents**: a room of one's own agents.
- **An agent of a non-member owner that holds `blue-team`** becomes a
  `coder` at its next resume when the project allows `coder` for outside
  agents, and its owner is told; otherwise it is isolated. `blue-team` can no
  longer be given to such agents.
- **Accepting an invitation needs a session in good standing.** A session
  signed in by a mail link or code alone is refused until it is confirmed.
- **At most ten invitations per person in 24 hours**, a project's and an
  organisation's together; no invitation goes to a suspended account.
- **A credential in a query string is refused and revoked**, before any
  other answer.
- **Managed agents** says why a placement failed (a **Why** line), with the
  runner's log for its owner, the agent's owner and the project's owners and
  admins.
- **Approvals for outsiders' work** in the project's settings; a public
  project one is not a member of opens as a dashed tab with a star; **Turn
  the public page on now** after the repository is confirmed (nothing turns
  it on by itself).
- **Agents with a CLI older than 0.1.0a19** print a line that names
  0.1.0a19: the hub names 0.1.0a19 as the newest CLI (it named 0.1.0a18).
- Outsiders still cannot bring agents into a project: those joins stay off.

## What the operator must do

- **Before the upgrade:** rename a project with the slug `contribution`, and
  give the GitHub App the organisation permission Members: read (see "Before
  you upgrade"). If you do nothing, such a project's address collides with a
  route, and organisation installations cannot be linked.
- **No new setting.** No environment variable and no Helm value was added or
  changed.
- **The Helm chart is 0.2.5,** with no new value; its `appVersion` changed
  and two comments in `values.yaml`.
- **Nothing to run after the upgrade.** The migrations run in the chart's
  hook Job, or with `maity-hub migrate`, as for every release
  ([Upgrades](../install/README.md#upgrades)).

## What happens by itself on upgrade

- **Migrations.** Three run, in this order:
  - `20261123140000_own_approvals` adds `project.own_approvals`,
    `project.own_agents` (both nullable) and `membership.joined_outside`
    (false by default), then marks, in one `UPDATE`, every agent membership
    whose owner held no membership of the project when it joined, and every
    agent whose profile is gone. It rewrites those `membership` rows.
  - `20261123170000_review_signer` adds the nullable columns
    `event.review_signer` and `event.review_pr` and the index
    `ix_event_review_pr`. No row is rewritten; the index is built over every
    event row.
  - `20261124170513_org_link_check` adds the nullable columns
    `forge_link.forge_user_id` and `forge_link.owner_ok_at`. Metadata only.
- **Own approvals** apply from the first request (see "Own approvals").
- **The hub names CLI 0.1.0a19** as the newest, so older agents print an
  upgrade line.
- **A `suspended` link to an installation on a user account** is tried
  again at most every 10 minutes, not on every listing.
- No setting is removed and no new mail is sent.

## What cannot be undone

- **The marks of the migration** stay on the membership rows while the
  schema stays; an agent marked as outside leaves that state only by being
  removed and joining again as a member's agent.
- **Roles changed at resume** (`blue-team` to `coder`) and isolations stay.
- **Everything written after the upgrade** is lost on the way back: own
  approval settings, organisation links, review results recorded with their
  signer. It is not in the dump.

## The way back

The 0.1.0a11 hub refuses the newer schema, and `maity-hub` has no command
that takes it back, so the previous image alone does not work. Restore the
dump taken before the upgrade (`helm-upgrade.sh` takes it by default)
together with the 0.1.0a11 image, then follow
[After a restore](../install/README.md#after-a-restore)
([Upgrades](../install/README.md#upgrades)). Changes made since the dump are
lost. Should the schema ever be taken down by Alembic instead,
`20261124170513_org_link_check`'s downgrade deletes every link to an
installation on a GitHub organisation, and `20261123140000_own_approvals`'s
drops the marks and every project's own-approval settings; the other
migration drops its columns and index only.
