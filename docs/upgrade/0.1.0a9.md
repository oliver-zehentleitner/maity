# Upgrading to 0.1.0a9

From 0.1.0a8. Released 2026-11-18. Changes in detail:
[CHANGELOG.md](../../CHANGELOG.md).

## Before you upgrade

Read these points first. None of them stops the upgrade, but each changes
what people on your hub can do from the first request after it.

- **Only a runner's owner places agents on it.** Creating a placement,
  changing its spec, starting and restarting it are for the runner's owner
  and the agents whose profile that owner owns, wherever the runner is
  attached. Anyone else, a project admin or an admin agent of another owner
  included, gets `403 forbidden` with `details.reason: "runner_owner_only"`.
  An agent's proposal goes to the runner's owner as a personal request;
  `policy.spawn_consent_by` no longer decides who answers it. A consent
  request filed as a project request before the upgrade is answered only by
  the runner's owner too (`docs/api.md` §15.4, §15.6). Placements that run
  at the upgrade keep running. The runner's owner sees every active
  placement on their runner, marked `foreign` where the agent's profile is
  someone else's, and may stop and remove it.
- **A pre-release tag no longer marks a project released.** A release card
  now takes its tag's PEP 440 version (`0.1.0a9`, `0.1.0rc1`) beside
  SemVer, but only a final version (no `-…`, no `a`, `b` or `rc`) sets the
  project's `released_at` when its tag is found, so the tag `v0.1.0a9`
  itself marks nothing released. A project already marked released stays
  so; the upgrade changes no stored value.
- **`PUT …/roles` needs `base_version`.** A script that writes a project's
  roles must send the `version` it read; without it the hub answers
  `400 invalid` with `details.fields.base_version: "required"`, and with a stale one
  `409 conflict` (`docs/api.md` §2.3 "Version."). The dashboard sends it.

## What changes for users

- **Roles in Settings.** Settings → Members and agents → **Roles** explains
  the built-in roles with their guides, and a human admin adds, changes and
  removes the project's own roles there. Of two admins saving at once, one
  wins; the other keeps the draft and is offered **Reload**.
- **The project's limit of agents on runners** (`max_placements`) is set in
  Project settings → Members and agents by a human admin, with a reason. A
  start refused with `placement_quota` names the limit and links there.
- **Managed agents** offers **Remove** on one's own placement too, not only
  on one someone else made, so an agent of one's own can be moved to
  another runner from there.
- **Runner owners** see the active placements on their runner across
  projects (`GET /runners/{id}/placements`), with `foreign` where the
  agent's profile belongs to someone else, and may stop and remove every
  placement on their runner, also in a project they are not a member of.
  The owner of an agent's profile may remove that agent's placement.
- **A reload band after a deploy.** An open dashboard page shows a band
  with **Reload** and **Later** once a newer dashboard is deployed. It never
  reloads by itself, and asks first while typed text is in a field.
  Pages opened before this upgrade do not have the band yet; reload them
  once.
- **A pasted image** in a chat's or a project message's text field becomes
  an attachment, like a picked file (PNG, JPEG, WebP or GIF, at most
  10 MiB).
- **Unread mentions are shown by the bell alone.** The line "1 unread
  mention" under a project's tabs is gone, and a mention no longer counts
  on a project's pill, on All projects or in the browser tab's title.
- **Admin → Instance** shows the hub's version, its database schema and
  every `MAITY_*` setting, with its value and whether it comes from the
  environment or is the default; secrets only as set or not set. Nothing
  can be switched there.
- **Refused spellings:** a website host, Mastodon name or Bluesky handle
  with a character outside ASCII, and a project role named `outside`, are
  refused when saved. Values stored before stay as they are.
- **Agents with a CLI older than 0.1.0a14** print a line that names
  0.1.0a14 and `pipx upgrade maity`, as on 0.1.0a8.

## What the operator must do

- **No new hub settings.** 0.1.0a9 adds no environment variable and changes
  no default. The Helm chart is unchanged apart from its `appVersion`.
  [`hub/README.md`](../../hub/README.md) now describes the GitHub App's
  five settings, `MAITY_ON_RUNNER_REVOKE`, `MAITY_MAX_PROJECTS_PER_OWNER`
  and `MAITY_MAX_ALIASES`, which earlier versions read already.
- **Scripts that write roles** send `base_version` (see "Before you
  upgrade"). If you do nothing, such a script's `PUT …/roles` is refused
  and the roles stay as they were.
- **Nothing to run after the upgrade.** The migration runs in the chart's
  hook Job, or with `maity-hub migrate`, as for every release
  ([Upgrades](../install/README.md#upgrades)).

## What happens by itself on upgrade

- **Migration.** One migration runs:
  `20261117100000_roles_version` adds the column `project.roles_version`
  (integer, not null, default `0`). Every project starts at version 0,
  whatever roles it holds. It rewrites and deletes no existing data.
- **Placements:** the runner-owner rule above applies from the first
  request. Placements that are running keep running; only creating,
  changing, starting and restarting them is limited.
- **`Maity-Web-Version`** is on every answer under `/api/v1/` and in the
  app shell.
- **A release card's version** is checked as SemVer or PEP 440. A spelling
  that is neither is refused with
  `details.fields.release.version: not_a_version`, which replaces
  `not_semver`.
- **Admin → Instance** and `GET /admin/instance` are there for the
  instance admin. No setting turns them on or off.
- No new mails, and no setting or key is removed.

## What cannot be undone

- **Roles saved after the upgrade** carry a version the previous hub does
  not know; the column is gone on the way back below, with everything
  written after the dump.
- **Everything written after the upgrade** is lost on the way back below.
  It is not in the dump.

## The way back

The 0.1.0a8 hub refuses the newer schema, and `maity-hub` has no command
that takes it back, so the previous image alone does not work. Restore the
dump taken before the upgrade (`helm-upgrade.sh` takes it by default)
together with the 0.1.0a8 image, then follow
[After a restore](../install/README.md#after-a-restore)
([Upgrades](../install/README.md#upgrades)). Changes made since the dump
are lost.
