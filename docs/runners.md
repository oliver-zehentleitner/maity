# Runners

A runner is a small service on one of your machines that starts agents for you, only in the projects and repositories you allow.

The hub never starts anything itself. You install the runner, and its configuration decides what it may do. A project without a runner works exactly as it did. Most people start without one: pasting a [join line](getting-started.md#join-your-agent) into a session you run yourself needs no runner.

## When you want one

- You want agents started and restarted on a machine without opening a session by hand.
- An agent with the right to propose should be able to bring in another member, with your consent where the project asks for it.

> [!NOTE]
> The runner needs tmux and runs on Linux and, without a system service, on macOS ([below](#macos)). It does not run on Windows: run it inside WSL. Every other `maity` command works on Windows.

## Pair a runner

1. In the dashboard, open **Runners** from the settings menu and fill in **Pair a runner**: a name for the machine's runner and the projects it is allowed in.
2. Choose **Create the pairing line** and copy the line.
3. On the machine, run it. It reads like this:

   ```sh
   maity runner pair https://<hub>/r/<token> --code <code>
   ```

   The credential goes to the runner's own state directory and is never printed. Without a configuration, `pair` writes `~/.config/maity-runner/runner.toml` with the hub and the state directory.
4. Add what the runner may do to that file:

   ```toml
   [limits]
   projects = ["you/demo"]
   repositories = ["github.com/you/*"]

   [harness.claude-code]
   modes = ["interactive", "supervised"]
   ```

5. Check it:

   ```sh
   maity runner check
   ```

   `check` exits with 1 on any error, and `--explain` shows the default of every key.

6. Start it:

   ```sh
   maity runner serve
   ```

   This runs in the foreground. To run it as a service, see `maity runner unit`. Until it runs, the runner stays offline and starts nothing.

> [!WARNING]
> Allow rules and hooks in the runner user's own harness settings are inherited by every agent it starts. `maity runner check` warns about them. Use a user of its own for the runner.

## macOS

On a Mac the runner works as on Linux, with these differences:

- **No service.** `maity runner install` sets up a systemd service and refuses on macOS; `maity runner unit` prints a systemd unit, of no use there. There is no launchd service yet. Run `maity runner serve` in a terminal of its own, for example as `caffeinate -i maity runner serve`, so the Mac does not sleep while it runs. Agents keep running when `serve` ends.
- **What to install.** [Homebrew](https://brew.sh), then `brew install tmux pipx gh`. pipx brings a Python 3.11 or later; the `python3` that comes with macOS is too old for `maity`. Install `maity` with pipx, and Claude Code and the forge login (`gh auth login`, `gh auth setup-git`) as the user the runner runs as.
- **Claude Code's sandbox is Seatbelt.** Where `sandbox-exec` is on the agents' `PATH` (macOS has it in `/usr/bin`), the runner switches Claude Code's sandbox on with the same strict settings as bubblewrap on Linux. `maity runner check` says `ok harness claude-code: OS sandbox (sandbox-exec)`. Without it, agents run unsandboxed, `check` warns and the placement reports `running` with `sandbox_unavailable`. Set `require_sandbox = true` under `[harness.claude-code]` to refuse such a start instead. If Seatbelt is there but cannot start, `check` still says `ok`, and Claude Code exits at every start instead of running unsandboxed: the placement restarts until it ends as `failed` (`crash_loop` or `hot_loop`), and its log (`maity runner logs <agent>`) shows Claude Code's own message.
- **The Keychain is not hidden.** On Linux, sandboxed commands cannot read Claude Code's login, because it is a file in the denied list. On macOS Claude Code keeps it in the Keychain, and so does `gh` by default, and the sandbox lets commands reach the Keychain service. Assume that any code an agent runs can read every login in the runner account's login keychain. Run the runner in a macOS account of its own, whose login keychain holds only the model login and a forge login you would hand to the agents. Whether a sandboxed command can read them has not been tried yet.
- **Case.** macOS's file system ignores case by default. maity's own checks of a clone's `.git` take that into account; whether Claude Code's and Seatbelt's deny rules match another spelling of a denied path has not been tried.
- **https remotes.** Claude Code's documentation says `git fetch` and `git push` over ssh fail inside Seatbelt even to an allowed host. Give the project an https repository URL.
- **One OS user.** Use the default `single` layout: agents run as the runner's user and can read its Keychain (above) and everything in its home except a [fixed list of secret files](../cli/README.md#maity-runner). Run the runner in a macOS account of its own rather than your own.
- **Only Claude Code.** Codex's sandbox and the ssh backend to a Mac host have not been tried on macOS.

The first run on a real Mac is still to come; [`maity runner`](../cli/README.md#maity-runner) has every setting.

## Start an agent on it

A project's runners are the **Runners** tab of its **Settings** (`/<owner>/<slug>/settings/runners`), for the project's admins: there you allow a runner of yours in the project and detach one. In the dashboard, the project's **Agents** page has the tab **Managed agents** (`/<owner>/<slug>/placements`). A project admin starts an agent on a runner of their own that is allowed in the project from **Join an agent** at the head of the page, in the form's last part **On a runner**. A member without admin rights, where the project lets members bring their own agents, may start an agent of their own that is not in the project yet on a runner of their own, within the limits its join line would have; it joins the project when the runner first starts it. The same form offers it to them, with only their agents that are not in the project yet and the fields their own join line would take; the API takes it too (`POST /api/v1/projects/<owner>/<slug>/placements` with `{"agent": {"id": "<agent id>"}, …}`). Changing such a placement afterwards needs admin rights, while its owner still stops and starts it. Everyone in the project sees where its agents run; the agent's owner or the runner's owner stops and removes them there, and only the runner's owner starts and restarts them. Only you place agents on your runner: attaching it to a project lets nobody else start one on it, and an agent's proposal for it asks you in person. Under **Runners**, each runner of yours lists **Agents on** it in every project, with **Stop agent** and **Remove agent** for each, even in a project you are not a member of; an agent placed there by someone else before this rule says so. **Managed agents** under **Agents** in the settings menu (`/agents/placements`) shows your own agents across your projects. Agents that may propose use the CLI:

```sh
maity runners
maity placement start <agent> --runner <runner> --tool claude-code --mode supervised --reason "<why>"
maity placement stop <agent> --grace 60
maity placement list
maity placement restart <agent>#<instance>
maity placement restart <agent> --fresh-session   # a reset: a fresh session, the same clone
```

`--fresh-session` is the dashboard's **Reset**: a restart whose agent starts on a fresh session of its tool instead of resuming the last conversation, the clone and its branches kept ([`docs/api.md` §15.6](api.md#156-placement-endpoints-proposals-and-consent)). Today a plain restart already starts fresh too; `--fresh-session` is the one that stays fresh once a restart resumes.

One agent may run on several placements at once, one per instance: on one runner or on several, as many as the agent's `max_instances` allows, which its owner sets (default 1). The hub counts the agent's active instances, the placements still waiting for their first credential and the new one, and refuses a placement beyond the limit when it is created or proposed (`instance_quota`). A further instance on the same runner works in a clone of its own, under a free name the hub picks: the agent's handle or the handle with a number ([`docs/api.md` §15.5](api.md#155-placements)), unless the placement names one. The dashboard's start form (**Join an agent**, **On a runner**) offers an agent that already runs as another instance while it has room, with how many of its instances run and where, and the clone it will get; at the limit it says that the agent's owner raises `max_instances` first. `maity placement list` shows each placement's agent as `<handle>#<instance>` once it has started. `maity placement stop` and `restart` name one placement as `<agent>#<instance>` or by its id; given just the agent while it has several placements, they refuse and list the placements' ids.

To move an agent of yours to another runner, off someone else's runner or from one of your runners to another: let it push its work and release its cards first, then stop it, set its retention as you wish, and remove it with **Remove** on its row under **Managed agents** (or **Remove agent** under **Runners**, on a runner of yours). The old instance counts against the agent's `max_instances` (above) until its credential is revoked and its placement has closed, so at the default of 1 a start elsewhere is refused (`instance_quota`) until then, and the dashboard's start form says the agent is at its limit and starts nothing; `placement_exists` refuses a start in a clone that an active placement on that runner already holds. Remove closes the placement at once or, while the runner may still be running it, wants it stopped and closes it when the runner reports it stopped. If the row stays and the runner never reports, a second Remove closes it at once. The exact rules are in [`docs/api.md` §15.5](api.md#155-placements) (**Closing**). The list shows active placements only. The API also lists closed ones, `GET /api/v1/projects/<owner>/<slug>/placements?closed=true`: those closed in the last 30 days, and older ones whose clone is still held; `GET /api/v1/projects/<owner>/<slug>/placements/<id>` reads one by its id. Once its row is gone, revoke the old instance's credential under **Agents**, so it no longer counts against the agent's instances, and start the agent again on a runner of your own. It starts as a new instance and claims its cards again; its membership stays, and no session or clone goes over. A card that was assigned to the old instance itself has to be assigned to the new one by someone who may assign cards in the project, a project admin for example. The old clone stays on the other runner until that runner's owner removes it (`maity runner gc --revoked`); removing it once the placement's retention time is up is not built yet (see [Clones after a stop](#clones-after-a-stop) below).

New agent profiles are created by a human in the dashboard, never from the CLI.

A project allows a limited number of active placements (agents on runners) at once, all runners together: 8 unless a human admin changes it under **Settings** → **Members and agents** → **Agents on runners**, which also shows how many placements are active now (a placement counts from when it is created, a proposal waiting for consent and one created stopped included, until it is closed, whether or not its runner has reported it yet). In the dashboard, a start beyond it is refused with the limit and a link there (`maity placement start` says `placement_quota`); lowering it closes no active placement.

After you update `maity` on a runner, restart the placements that were already running. The runner records the agent's clone at each start, and `maity` in a session started by an older runner runs no git ("`MAITY_GIT_INODE` is not set … restart the placement").

A runner whose configuration lists `[harness.codex]` needs a hub of 0.1.0a8 or newer. Codex has no command allowlist of its own: its OS sandbox is the boundary, and the runner advertises it as `confinement: "sandbox"`. An older hub does not know that value, refuses the runner's hello (`invalid`, on `capabilities.harnesses.<n>.confinement`), and the runner stops. Until the hub is updated, leave codex out of the runner's configuration.

By default, agents running Claude Code write no attribution lines: the settings the runner passes with `--settings` tell Claude Code to leave out the `Co-Authored-By` trailer on commits and the "Generated with Claude Code" line in pull request bodies. Placements that were already running get this only after a restart. It is a default that steers the model, not a guarantee: managed settings on the machine, or an explicit instruction such as one in the agent's `CLAUDE.md` or memory, can still add the lines. The agents' user's own Claude Code settings cannot, because `--settings` takes precedence over them.

The runner owner can ask a runner to look for a newer version of one of its tools at once ("Update now", `POST /api/v1/runners/<id>/updates` with `{"tool": "claude-code"}`), for a tool the runner reports it updates; the runner view (`GET /api/v1/runners/<id>`) shows the tools a runner reports (`capabilities.tools`: version, kept version, latest, state) and the open requests (`update_requests`). The dashboard has no button for it yet. What the runner does with it: [Keeping Claude Code and Codex current](#keeping-claude-code-and-codex-current).

## Ubuntu: nested user namespaces

On Ubuntu (seen on 26.04), AppArmor's profile `bwrap-userns-restrict` (package `apparmor`) lets bubblewrap start but takes every capability from what it starts. Claude Code's sandbox needs exactly that: its seccomp step opens a second user namespace inside bubblewrap. A Claude Code placement then starts and its session runs `maity`, but every sandboxed command fails, a subagent's included, with `apply-seccomp: write /proc/self/setgroups (nested userns is capability-restricted; caller must provide CAP_SYS_ADMIN): Permission denied`.

On the local backend, `maity runner check` starts that nesting once as the agents' user, with their `PATH` and each command by its absolute path (`bwrap … -- unshare --user --map-root-user true`). It has three answers:

- `ok harness claude-code: a user namespace starts inside bubblewrap`.
- An **error**, `… does not start inside bubblewrap (…uid_map…)`, only when unshare could not map the user in the inner namespace: the case above.
- A **warning**, which blames nothing, when the probe could not tell: a timeout, a failure to start, bubblewrap itself not starting, another error, or `bwrap`, `unshare` or `true` missing from `agent_path`.

On macOS, where the sandbox is Seatbelt, the probe does not run. **On an ssh host it does not run either**: `runner check` there does not detect this lock, so check such a host by hand with the command above as the agents' user.

The fix is on the host, needs root and is the operator's call. One change is verified on an Ubuntu 26.04 runner: in `/etc/apparmor.d/bwrap-userns-restrict`, in profile `unpriv_bwrap`, the line `audit deny capability,` replaced by `allow capability,`, then `apparmor_parser -r /etc/apparmor.d/bwrap-userns-restrict`. After it the check's probe passes, and in a running Claude Code agent the `apply-seccomp` error was gone for the session and for a subagent. A `local/` include cannot lift a deny, so the file itself changes. That affects every bubblewrap sandbox on the host (Flatpak, for one), and a later `apparmor` update asks before it overwrites the file. Keep a copy of the original to go back.

Claude Code's own documentation names two other ways that have not been tried on a Maity runner: an AppArmor profile of its own for `/usr/bin/bwrap`, which carries the same profile name as Ubuntu's, so the two may collide, and `sysctl kernel.apparmor_restrict_unprivileged_userns=0`. A public report (anthropic-experimental/sandbox-runtime#429) has that sysctl at 0 and the failure still there.

## Claude Code: Unix socket blocking

On Linux, Claude Code's sandbox runs every sandboxed command behind a seccomp step that refuses to open a Unix socket. Every placement on a host runs as the same OS user, so that step is what keeps one placement out of another placement's sockets and the agents' tmux server. Where the step cannot run, Claude Code still runs the command in its sandbox, with Unix sockets allowed. Its `failIfUnavailable` setting, which the runner sets, covers only a sandbox that cannot start at all. **Nothing in Claude Code's interactive interface shows whether the socket block is on**: its warning goes to a debug log that writes nothing by default, and even with that log switched on nothing reaches the session while it runs. So the runner checks it itself, in two parts: a preflight before every start, and a probe in `maity runner check`.

Before every start of a sandboxed Claude Code placement, and in `maity runner check` (locally and on each ssh host), the runner checks two things as the agents' user:

- **The machine** (`uname -m`): `x86_64` or `amd64` (Claude Code's `x64`), or `aarch64` or `arm64` (`arm64`). Claude Code 2.1.328 and 2.1.329 support their seccomp step on these two only; 32-bit x86 and every other machine run without it.
- **The kernel's seccomp filtering**: `/proc/self/status` must have a `Seccomp:` line, and on Linux 5.9 or later a `Seccomp_filters:` line too. Their values do not matter, only that the kernel has them (each must read as a number).

`check` says `ok harness claude-code: seccomp for blocking Unix sockets: machine x64, kernel seccomp filtering present` (`arm64` on such a machine). Otherwise it reports an error naming the machine or what is missing, and the runner refuses every sandboxed Claude Code start on that host (`failed`, `harness_refused`, the reason in its log). An answer the runner cannot read (an unreadable `/proc/self/status`, a value that is not a number, no machine from `uname`) refuses the start too. Once the check has passed, the runner keeps the result until it restarts; the machine and the kernel do not change while it runs, and a reboot restarts it. On an ssh host the result is kept only while the host stays reachable: the machine that answers under that name when it is back may be another one, so the check is read again. A failed or unreadable check is read again at the next start.

The preflight covers what the host must give Claude Code. On a supported machine the block also depends on Claude Code handing its built-in seccomp helper to the sandbox, which a look at the host cannot show. So after a passing preflight, `maity runner check` (never a placement start) runs the installed Claude Code once headless as the agents' user, with the sandbox on as a placement has it and the sandbox's debug log switched on, and asks it to run one harmless command. It reads only the sandbox's own lines from the run, never the model's answer:

- `ok harness claude-code: probe run: Unix socket blocking applied`: the sandbox applied the filter.
- An error that the block is off: Claude Code found no seccomp helper, so its commands run with Unix sockets open. Do not run Claude Code placements on that host.
- An error that the block is not confirmed: a timeout, a non-zero exit (a missing Claude login, for example), output that cannot be read, or neither line. Treat the host as unprotected until the probe passes.

`check` reads the hook and Unix socket settings (below) first. While either refuses every sandboxed start, the probe does not run (`warn harness claude-code: probe not run: the settings above refuse every sandboxed start`) and no pass is kept.

The probe spends one small prompt on the agents' Claude login. **Run `maity runner check` after every change of the Claude Code version** the runner installs, and on every new kind of host: the probe is how a new version is shown to keep the block on. The preflight is still what holds back a start; a failed probe is reported, not enforced.

`check` keeps, per host, the Claude Code version whose probe passed (`claude-probe.json` in the state directory), and forgets it when the probe does not pass or is not run for the settings. At each sandboxed Claude Code start the runner compares it with the installed version. When they differ, or no probe has passed on that host, the start goes ahead and the log says, once per host and installed version while the runner runs, `harness claude-code: the Unix socket probe last passed with <version>, installed <version>; run maity runner check`. `check` reports the same line as an error when its own probe does not pass or is not run; a probe that passes in that run records the version first, so it adds no such line. The runner installs and updates Claude Code itself, so a start is not refused on this alone.

Both checks are Linux only. On macOS the sandbox is Seatbelt, which has no seccomp step, and nothing is checked.

**The placement pins its Unix socket settings and refuses user settings that would change them.** The settings file the runner gives each sandboxed Claude Code placement sets `sandbox.network.allowAllUnixSockets` to `false`. Placements also load the agents' user's own `~/.claude/settings.json` (`--setting-sources user`). While that file carries any of `sandbox.network.allowAllUnixSockets`, `sandbox.network.allowUnixSockets` or `sandbox.seccompConfig`, whatever the value, every sandboxed Claude Code start on that host is refused (`failed`, `harness_refused`, the reason in the log), and `check` reports it as an error. A settings file that cannot be read as a JSON object refuses the start too. The managed settings (`/etc/claude-code/managed-settings.json` and the `*.json` files in `managed-settings.d/` beside it) win over the placement's file, so the same keys there refuse the start as well, and so does an unreadable managed file. Remove the setting; the runner reads the files again at the next start. With none of them set, `check` says `ok harness claude-code: the managed and user settings carry no Unix socket setting`.

## Antigravity (agy)

The runner has an adapter for Google's Antigravity CLI, `agy`, and **now offers the `antigravity` harness.** A configuration with `[harness.antigravity]` is accepted by `maity runner check` and `serve`. agy keeps one command grant the runner cannot fully confine from its own settings — `command(maity)`, which agy applies after reading the invoked command past a leading assignment or wrapper — so agy runs with a known residual risk, which the owner accepted (`req-9spwe33neh1z`). OS-level confinement of that command is being added incrementally (`tsk-zjv2xyhyggnm`).

It is configured as:

```toml
[harness.antigravity]
modes = ["supervised", "interactive"]
```

Install agy for the user the agents run as (`~/.local/bin/agy`; add that to `agent_path` if the service's `PATH` lacks it) and sign in once by running `agy` as that user. Without a desktop keyring agy keeps the sign-in as a file in `~/.gemini/antigravity-cli/`, which `maity runner check` looks for, and the onboarding questions of the first run are answered there once, not by the runner.

**A workspace folder per placement.** agy loads the hooks, MCP servers, plugins, skills and rules of the directory it starts in, even headless and in a folder nobody trusted, and its hooks and MCP servers run outside its sandbox. So an antigravity placement gets a folder, `<workspaces>/<project id>/<clone>`, with the clone as `repo` inside it. agy starts in the folder, and the start prompt tells the agent to `cd repo`, read `repo/AGENTS.md` and work only there. Before every start, and in `supervised` mode before every run of the loop as well, the runner checks the folder and starts nothing (`failed`, `workspace_in_use`) when

- it holds anything besides `repo`, such as a `GEMINI.md` or `.agents/` a run left there (`workspace_not_bare`), or
- a directory above it, up to `/`, has an entry `.git`, so it lies inside a git work tree whose configuration agy would load, or its path goes through a symbolic link (`workspace_in_repository`).

An agent that sends a review from the folder (`maity say --type review_result`) has its cites checked in the clone, `repo`, whichever directory it is in: maity checks them in the runner's clone, never in the folder, which is no clone.

The runner deletes nothing in the folder. The service's log names what it found, without file contents; remove the entry by hand and restart the placement. Keep the workspaces root out of any git repository: `maity runner check` fails when it lies inside one. A clone does not move between the two layouts: an existing plain clone at the folder's path, or a folder at a plain clone's path, is refused as `workspace_in_use`.

**Session settings.** Before each start the runner writes the settings agy gets for that session with `--settings`, in the runner's own directory for the agent, outside the folder:

- `agentMode` set to the default mode, not `auto` (agy's default since 1.5.7), whose reviewer model may let a command leave the sandbox;
- `toolPermission: proceed-in-sandbox` and the terminal sandbox on: a command that no rule names runs inside the sandbox without asking;
- the workspace folder trusted, so an interactive start asks nothing;
- denied to the file tools: the clone's `.git/maity` (the agent's credential), writing `.git/config`, `.git/hooks` and the rest that makes git run something, the other clones' credentials, the runner's state and configuration, the secrets in the agents' home and agy's own sign-in;
- allowed: `maity` and reading the hub's, the forge's and the grant's `network` hosts; the repository's `allow` command list is not applied to agy (see below).

An allowed command may leave agy's sandbox. `maity` has to, for its credential and the network, and outside the sandbox any allowed command can read the credential, as with Claude Code. A grant's `allow` command list is not applied to agy, though (see below), so for agy only `maity` runs outside the sandbox. Run every `maity` command alone; a line that chains it with another command is refused outside the sandbox.

**Command grants are not applied to agy.** agy reads the invoked command from the line — stepping over a leading environment assignment or command wrapper — before it matches its own `command(...)` rules, which is not how Claude Code matches an entry. A command grant therefore cannot be reproduced for agy the way Claude Code applies `Bash(make test)` or `Bash(python3 -m pytest *)`, so the runner does not give agy a rule for a grant's `allow` command list at all. For each entry of the `allow` list:

- an entry without `*`, such as `make test`, and an entry ending in ` *`, such as `python3 -m pytest *`: no rule. Each is left out, named as a warning by `maity runner check`, and runs inside agy's sandbox like every unlisted command;
- an entry with another `*` (`npm run test:*`): nothing either, and no warning. agy's rules cannot say it, since a rule word is matched on its own, so it runs inside the sandbox like every unlisted command.

So agy is given only `command(maity)` and the `read_url` hosts; a repository's `allow` command list reaches Claude Code unchanged, but not agy or Codex.

**This narrows what agy runs outside its sandbox.** Earlier runner versions gave agy a command grant as a rule — an exact entry, then also a ` *` prefix — so a `make test` or `python3 -m pytest *` grant ran outside agy's sandbox. It no longer does: a command grant now runs inside the sandbox, like an unlisted command. A placement cannot make a repository command run outside agy's sandbox through the `allow` list any more; arrange such work another way, or run it under Claude Code. The rules here come from agy's documentation and from reading agy 1.5.9's matching code.

**One command grant remains for agy: `command(maity)`.** The runner must let the session reach the hub, so `maity` runs outside agy's sandbox, as it does for every harness. agy applies that one grant the way it applies any command rule — after reading the invoked command from the line, past a leading assignment or wrapper — so for agy it is not as tight a boundary as Claude Code's `Bash(maity *)`. No agy setting tightens it, and the runner cannot close the gap from its own settings. This is a known residual risk of running agy; the owner accepted it (`req-9spwe33neh1z`), and the harness is offered with that risk open. Confining `maity` at the OS level, so that line cannot reach around the grant, is being added incrementally (`tsk-zjv2xyhyggnm`).

**The agents' user's own agy settings apply too.** agy merges the session settings with that user's `~/.gemini`: its allow rules widen every agent's grant, and its global rules, skills, hooks, MCP servers and plugins load for every agent, the hooks and MCP servers outside the sandbox. The runner neither reads nor changes them, apart from the warnings in `maity runner check` about allow rules in `~/.gemini/antigravity-cli/settings.json` and servers in `~/.gemini/config/mcp_config.json`. Keep that home free of anything agents should not run, ideally with a user of its own for the agents.

**Modes.** `supervised` runs `agy -p` on each event and continues with `-c`, which agy scopes to the working directory, so to the placement's own folder. `interactive` runs `agy -i` with the start prompt in the tmux pane, and after a restart for silence resumes the folder's last conversation with `-c`. agy's exit code for a provider limit is not known yet, so a limit ends a run like any other failure.

**The sandbox.** On Linux agy's terminal sandbox runs commands in kernel namespaces, and where they cannot start agy runs commands without it, without saying so. The runner may advertise `sandbox: on` only where it has seen agy's sandbox start, and agy has no command that starts only its sandbox without a model call, so for now the runner advertises `sandbox: off` for agy on every host: a placement reports `running` with `sandbox_unavailable`, and `require_sandbox = true` under `[harness.antigravity]` refuses it. The session settings still switch agy's sandbox on; only the report is off. `maity runner check` tries, as the agents' user, whether the namespaces agy's sandbox needs start (user, mount, PID and network, with `unshare`) and says so as a diagnostic ("agy's sandbox start not verified"); where they do not (a kernel or AppArmor setting that blocks unprivileged user namespaces), agy runs commands unsandboxed.

Two things have not been tried in a real session yet: whether `git fetch` and `git push` reach the forge from inside agy's sandbox, and whether the deny on `.git/config` reaches the sandbox too. The runner gives each agy session the same three git settings as a sandboxed Claude Code session (below), so git works either way.

## OpenCode (Grok)

The runner has an adapter for the OpenCode CLI, `opencode`, running **Grok**, and **now offers the `opencode` harness.** A configuration with `[harness.opencode]` is accepted by `maity runner check` and `serve`.

**opencode's command and permission rules are not a security boundary.** opencode has no OS-level sandbox the runner switches on, so the deny/allow rules the runner writes are model-steering configuration, not a boundary. **Treat an opencode agent as able to run any command as the agents' OS user** — anything that user can read, write or reach, it can. **Run opencode's agents as a separate OS user**, isolated from the runner and from the other harnesses, so that what an opencode agent can reach is only that user's own files. The owner accepted this residual risk (`req-kezp8rppfhn5`, "ship now, harden next"); the planned hardening is an OS-level sandbox for opencode, for example bubblewrap (`tsk-nynpvag9zvhh`). opencode was first offered under `req-g4d2cskx6zxv`, on the evidence of a 2026-11-15 spike that ran opencode green (5/5), passed the limit run and ran Grok reviews.

It is configured as:

```toml
[harness.opencode]
modes = ["supervised", "interactive"]
models = ["<provider>/<model>"]
default_model = "<provider>/<model>"
```

**Models.** opencode runs **Grok**. opencode names a model as `<provider>/<model>` (its own model selector), so name the Grok model that way under `models` — the provider and Grok model id your account uses — and set `default_model` to the one a placement uses when it names none; `maity runner check` refuses a `default_model` that is not in `models`. The value passes through to `opencode --model`. A placement that names no `model` starts on `default_model`; the start log names the model in effect. The runner **fails closed on the model**: if the effective model (the placement's, or `default_model`) is not one of the configured `models`, the start is refused (`failed`, `harness_refused`) instead of launching. A provider-`opencode` model is opencode-hosted, so running one — including the free default opencode would pick with no `--model` — would send the clone's conversation to opencode's servers rather than to the provider you configured. The dashboard's start form offers OpenCode only with one of the `models` its runner names, with no "runner's default" and nothing sent until one is chosen, and leaves OpenCode out, saying why, where the runner names no `models`.

**Modes.** `supervised` runs `opencode run` on each event and continues the same conversation with `--continue`. `interactive` runs `opencode --prompt` with the start prompt in the tmux pane. opencode's exit code for a provider limit is not known yet, so a limit ends a run like any other failure.

**Install and sign in as the agents' user.** Install opencode for the user the agents run as (opencode's installer puts it in `~/.opencode/bin`; add the directory that holds the binary to `agent_path` if the service's `PATH` lacks it) and sign in once by running `opencode` as that user, so its login lands in that user's home where opencode finds it. The runner neither signs in nor reads that login. The runner hides the listed home secrets from the sandboxed harnesses, but opencode runs without a sandbox, so an opencode agent is not kept from them: give opencode's agents an OS user of their own, whose home holds nothing other agents or the runner rely on.

**The permission configuration the runner writes.** These rules steer the model and shape what an agent normally does; they are configuration, not a security boundary (above). Before each start the runner writes an `opencode.json` in its own directory for the agent and points opencode at it with `OPENCODE_CONFIG`, with `OPENCODE_DISABLE_PROJECT_CONFIG=1` so the repository's own `opencode.json` and `.opencode/` directories (agents, commands, plugins) do not win over it. The configuration denies tools by default and then allows:

- `bash`: `maity *`, the fixed Keep the Why UUID command, the named `git` subcommands and the repository's `allow` command list; `maity` is allowed only as one plain call;
- `read` everything but the clone's `.git/maity` (the agent's credential); `edit` everything but the clone's `.git`; `list` on; `grep` and `glob` off;
- `webfetch` and directories outside the clone denied.

`AGENTS.md` is named as an instruction, since the project configuration is switched off.

**The runner advertises `sandbox: off`.** opencode has no OS sandbox the runner switches on, so the permission configuration above is not an OS boundary. Assume an opencode agent can run any command as the agents' OS user, so keep that user away from the runner's own state and from the other harnesses' clones and logins — a separate OS user for opencode's agents. The owner accepted this residual risk (`req-kezp8rppfhn5`); the planned fix is an OS-level sandbox for opencode, for example bubblewrap (`tsk-nynpvag9zvhh`).

**opencode is not a boundary between placements.** opencode has no OS sandbox. Its `external_directory` setting limits only opencode's file tools; commands it runs can read, write and connect to everything the agents' user can, including other placements' scratch directories and sockets. A scratch is therefore not private in an opencode placement, and opencode is not a boundary between placements on the same host.

`maity runner check` reports the missing OS sandbox for opencode on both backends — the local one and each ssh host, whose line carries a `<host>: ` prefix. A missing binary or a failed `--version` errors out first; otherwise `check` keeps the `ok harness opencode` line and adds a `harness opencode: no OS sandbox` one. Because every opencode placement is unsandboxed, `require_sandbox = true` under `[harness.opencode]` makes that an **error** (the start is refused, like claude-code and antigravity); without it, it is a **warning**.

## When an agent goes quiet

An interactive agent listens by running `maity wait`. If that stops (a full disk, a provider limit, a turn it closed), the agent sits at its prompt and its placement still shows as running. The runner notices it by itself: when nothing runs in the session (no `maity wait`, no command the agent started) and the screen has not changed for 30 minutes, it types one line into the session asking the agent to go back to its wait loop. Any answer counts. If the session does not react at all in the next 10 minutes, or the agent has answered three such lines without going back to its wait, the runner restarts the session, and Claude Code picks up its last conversation. **Managed agents** then shows the restart as `hung`. An agent that goes quiet again after every restart is restarted at most five times in a row; then its placement is held as failed until someone restarts it. Once it runs its wait again, the count starts over. A long build or test run is never taken for silence: the command running counts as work. The two times are fixed for now; they become the agent owner's settings with the hub's health settings.

**The runner's watch: not built yet (tsk-twmms66p1ww4).** What follows up to the settings is planned, not built: today only the check above runs. A session can also stop listening while something still runs in it, for example a `maity wait` that no longer hears the hub, and a placement can show as running although its agent never joined. The hub knows both; the runner will read them on each placement it runs and look for the cause before it does anything:

- **It looks** when the hub has said for `not_listening_grace_minutes` that the agent's session is not listening, or when no session of the agent started within `join_within_minutes` of the runner starting it.
- **It finds a cause**: the tool exited; nothing runs (no `maity wait`); a `maity wait` runs but does not hear the hub; the agent never joined; the tool exited for its usage limit; its login is gone, as the tool's own login check says; or none of these (`unknown`). Text on the screen alone never decides a usage limit or a gone login: the runner notes it, but it needs the tool's limit exit or its login check too. A tool without a login check (agy) is never taken for a gone login. A command still running in the session counts as work, as in the check above, for up to `tool_call_max_minutes` (120 minutes by default) of not listening; after that the cause is `unknown`.
- **It reacts by cause.** An exited tool, a deaf `maity wait`, a missing join or an unknown cause: one restart, which resumes the agent's last conversation, as **Restart** does, never a fresh session (that stays **Reset**). Nothing running: one line typed into the session, as above, once while the hub reports the same quiet spell. A usage limit: it waits for the reset and starts the agent then. A gone login: no restart; the runner ends the session, the placement stops as failed (`auth`) and you get a request in your inbox, since only you can sign the tool in again. A refused join is reported at once, when the hub refuses it, with the hub's code and no restart, as today.
- **It never ends a session you are attached to.** While someone is attached to the agent's tmux session, the runner ends nothing and types nothing: it only reports what it found, and looks again once the last person has detached. If tmux cannot say whether someone is attached, the runner assumes someone is.
- **It stops after the second failure.** Only the causes it would restart for count: after `auto_restarts` restarts within `retry_window_minutes`, the next one is not made. The runner ends the session if it still runs, the placement is held as failed (`hung`, with `not_listening` or `never_joined`), and you get the same inbox request as for any stopped agent. Restart it yourself once you know why. A usage limit, a gone login, a refused join or a typed line never count toward it. A restart the check above makes after the typed line counts toward that check's own limit of five in a row, not here.
- **It leaves resting agents alone.** An agent that is paused or dormant is never restarted for being quiet, and the check above leaves it alone too. An isolated agent's placements are closed anyway.
- **It writes down what it found.** Each time, the placement's report carries the cause and what the runner saw, as fixed codes only: never the screen's text, a path in the agent's home or a secret. With it go the runner's own last log lines about that placement alone (its starts, exits, restarts and warnings, in the runner's own words, with paths, branch names and error texts from the agent's side replaced by placeholders, never the session's output), which only you as the runner's owner, the agent's owner and the project's owners and admins (trust `owner` or `admin`, an admin agent such as the lead among them) can read.
- **Agents of other people.** An agent placed on your runner by someone else before 2026-11-16 keeps running, but the hub does not show your runner that agent's session state. For such an agent the runner acts only on what it sees itself: the tool exiting, its limit, its login, a refused join.

The settings, in the runner's configuration:

```toml
[limits.watch]
not_listening_grace_minutes = 15
join_within_minutes = 10
auto_restarts = 1
retry_window_minutes = 120
```

| Setting | Default | Range | What it does |
|---|---|---|---|
| `not_listening_grace_minutes` | 15 | 1-1440 | how long the hub must have seen the session not listening before the runner looks |
| `join_within_minutes` | 10 | 1-120 | how long after a start the agent has to join before the runner looks |
| `auto_restarts` | 1 | 0-3 | how many restarts the watch makes within the window, for the causes it restarts for; `0` holds the placement as failed at the first finding that would restart it |
| `retry_window_minutes` | 120 | 10-1440 | the window in which those restarts are counted |

`not_listening_grace_minutes` is a runner setting until the hub sends each agent owner's health settings; then the owner's `hang_after_minutes` takes its place.

For every Claude Code placement the runner sets `CLAUDE_CODE_DISABLE_BG_SHELL_PRESSURE_REAP=1` in the start environment, so Claude Code's background-shell memory-pressure reaper does not stop the placement's background `maity wait` under low memory and leave the session running but no longer listening. This turns the memory-pressure stop off for every background shell of the placement, not only the `maity wait`; the host's own memory limits still apply — the runner sets none of its own, so under memory pressure a placement's background shells are bounded by the kernel OOM killer and the operator's unit or cgroup limits, and the lever on a host is how many agents it runs.

The runner never types while someone is attached to the session: attaching pauses the check.

**Codex's folder prompt.** An interactive Codex asks at its start about the clone, which the runner marks untrusted so that the repository's own Codex configuration is not loaded. Within three minutes of a start it made, and with nobody attached, the runner answers that prompt with its restricted choice ("Open restricted"), which keeps the clone untrusted, and logs it. It never answers a prompt that would trust the folder: the log then says the session is `waiting on a first-run prompt`, and someone has to attach and answer it. While a folder prompt shows, also one that shows later, the runner sends no idle line or key into that session; once someone has answered it, the check for silence runs as before.

## Git in an agent's session

The sandbox keeps an agent's `.git/config` read-only, because what it sets could run a program outside the sandbox. It does so by holding an empty `.git/config.lock`, which blocks git's own writes to `.git/config`; a placed clone may therefore carry that empty placeholder, and the runner's clone check accepts it while it is empty. A non-empty `config.lock` makes the clone `not_a_plain_clone` (`workspace_in_use`), the same as a `config.worktree` with content. The runner gives each sandboxed session `branch.autoSetupMerge=false`, `push.default=current` and `fetch.recurseSubmodules=false` through the environment, overriding the clone's own values for these three keys (a runner's clone is a plain one), so `git switch -c <branch> origin/main`, `git push`, `git pull origin <branch>` and `maity report` work without an upstream. `git push -u` and `--set-upstream` push but cannot store the upstream and print an error, `--track` fails, and `git branch -m` renames the branch and then fails on the configuration; `git branch -D` deletes the branch and warns that it could not update the configuration. Before a sandboxed Claude Code start, the runner lists the placeholder paths the sandbox fills in the work tree in the clone's `.git/info/exclude`, so `git status` does not show them; a path that already has content is not listed and stays visible. To let agents open their pull requests themselves, set `pull_requests = true` in the repository's grant ([`maity runner`](../cli/README.md#maity-runner) has the lines). Agents then use `maity gh pr create` and `maity gh pr view`, which always work on the clone's own repository. For a lead that runs as a placement, also set `lead = true` (default off; without `pull_requests = true` it gives nothing, and `maity runner check` warns): a placed member whose role the hub names `manager`, or a project role built on manager, then also runs `maity gh pr merge` (a squash merge only, by number, with the head's full sha in `--match-head-commit` required, and only a direct one: maity reads GitHub's merge-queue state for the pull request through `gh api graphql` and refuses on a merge queue or when it cannot read it), `pr edit` (title and body only, set with one REST call, `gh api --method=PATCH` on the pull request of the clone's own repository, so it does not depend on gh's version), `pr ready`, `run list --commit <sha>` and `run view <run id>` (the jobs by name, or with `--log-failed` the last 400 lines of the failed steps' log). maity reads the role from the hub at each of these calls, for the member `GET /me` names for the session's credential and never from local state, and refuses when the hub does not answer, for an isolated member, when `MAITY_STATE_DIR` is set, and when the runner's directory for the agent is not this placement's (`agents/<placement id>/git` where the runner keeps the agents' files, the runner's state directory in the `single` layout and the agent user's `~/.maity-runner` in the `agent_user` and ssh layouts, reached with no link, all three directories the agents' user's and none writable by group or others; the runner keeps `agents/` at 0700 itself). The session they sign with is read through the clone's checked `.git`, never by a path; on Windows, where maity cannot read it that way, the lead commands are refused. What gh prints is cleaned before it reaches the terminal. On agy and opencode, which are no boundary between placements, none of these checks is a boundary either. Like every `maity gh` call, these reach no other repository, run no other gh command and pass gh no free-form argument. The [CLI README](../cli/README.md#maity-runner) lists each command's shape. A Codex placement never gets `lead`, for the same reason it gets no `pull_requests`. `maity gh` passes gh only `HOME`, the locale, the temporary directory, proxy and certificate variables, so gh must be logged in as the agents' user, with the login stored where gh finds it under `HOME`: a login given through `GH_TOKEN`, `GITHUB_TOKEN`, `GH_CONFIG_DIR` or `XDG_CONFIG_HOME` does not reach it. Under the harness's sandbox no placed session can run gh itself, and a gh entry in `allow` is ignored with a warning from `maity runner check`. With its sandbox on, a Codex placement starts without the grant's `allow` list and `pull_requests`: Codex's `maity` runs inside its sandbox, and the runner sets up `maity gh` only for a `maity` that runs outside it, so it gives a Codex placement no pull-request grant and does not mention `maity gh` to it. With its sandbox off, such a grant refuses the Codex start. Four gaps are still open. First, `git push` in the sandbox uses the machine's forge login, so code that an allowed command runs (tests, builds) can push to any repository that login may push to. Second, without the harness's sandbox (opencode, Claude Code outside Linux and macOS, or on Linux without bwrap and socat, or older than 2.1.295 or of an unknown version) the deny rules are no boundary: repository code can run gh itself. Third, on an ssh target gh must be at the path the runner found on its own host, or `maity gh` refuses. Fourth, with Codex the runner does not grant pull requests, but it does not enforce that either. A `.git` that sandboxed code renamed or replaced is refused: `maity gh` reads the record only from the `.git` the runner recorded when it started the session (restart placements after an update, as above). A Claude Code agent runs every `maity` command alone, as one plain call: the runner's hook refuses a line that starts with `maity` as its first word, or with assignments to `NO_COLOR`, `LANG`, `LC_*` or `TZ` and then `maity` (`TZ=UTC maity status`), and pipes, chains, redirects, sends it to the background (`&`), substitutes (`$(...)`, backticks) or holds a heredoc, a newline or an unescaped `$` outside single quotes. Anything else before a word `maity` (an assignment to any other name, every `MAITY_` variable included, so a wait's timeout goes in `maity wait --timeout N`, or with `+=`, another command by name or path, a shell keyword, `!`, a redirection, a subshell or a group, or `maity` by a path) refuses the line outright, text that mentions `maity` as a word after another command included. A word counts as `maity` or `runner` also once the backslashes and quotes in it are taken off, and a word with a brace also as each of its alternatives (the parts between `{`, `,` and `}`) and as each word its brace expansion makes, the alternatives joined with the text around them (`ma{ity,}` counts as `maity`), as Bash expands its braces, quoted and escaped characters as text, up to 256 words: a word whose braces make more refuses the line. A command substitution in any form (backticks included, also inside double quotes, or `$(…)`) that names `maity` is refused, and so is `maity` with an expansion glued right after it. The hook guarantees that a line Claude Code may take out of the sandbox, `maity` after only the allowed assignments, runs only as one plain call; names assembled from expansions are left to the sandbox and to the CLI's own guard. A line with `$'…'` or `$"…"` text, a backslash-newline, or `eval`, `source`, `.`, `trap` or `bash -c` with a quoted or expanded word is refused whatever it holds. A word whose path ends in `/maity` (in any case) counts as `maity` wherever it stands, so `cd /some/path/maity && make` is refused; a path whose last part only starts with `maity`, such as a clone directory named after a handle (`cd /some/path/maity-coder-claude-004 && make`), is no `maity` word. Text goes in single quotes, or in a file in the clone passed with `--body-file`. A line in which a word `runner` follows a word `maity` is refused, also when `runner` is only text, quoted or not: `maity runner` is the runner's own command, and the runner never starts it through an agent's tool call. A line that names `maity` anywhere is refused when it holds a comment, a heredoc or more than one line, so each `maity` command goes on a line of its own, without a comment. A line that names `maity` and holds a control character other than a tab or a newline (a carriage return, a vertical tab, a form feed) or a space other than the ASCII one (a no-break or other Unicode space, a zero-width space) or an invisible format character (Unicode category Cf: a zero-width joiner, a word joiner, a soft hyphen, a bidi control) is refused as well, since the shell does not split words there. Where a line's `maity` runs inside the sandbox, the sandbox hides the clone's credential from it. The hook refuses a call when it fails or times out only from Claude Code 2.1.295, so the runner switches Claude Code's sandbox on only for 2.1.295 or later. On a host where the sandbox's tools are there (bubblewrap and socat on Linux), an older or unknown version, a prerelease of 2.1.295 included, refuses the start (`failed`, `harness_refused`), and `maity runner check` says so as an error. A version Claude Code prints in another shape than a plain version (`2.1.295+`, `2.1.295-_dev`) counts as unknown. To run such a version unsandboxed on purpose, set `require_sandbox = false` under `[harness.claude-code]`; `check` then only warns. A host without the tools runs Claude Code unsandboxed as before, with a warning, unless `require_sandbox = true`. Managed Claude Code settings (`/etc/claude-code/managed-settings.json` and the `*.json` files in `/etc/claude-code/managed-settings.d/`; on macOS under `/Library/Application Support/ClaudeCode/`) that set `disableAllHooks` or `allowManagedHooksOnly`, and the agents' user's own settings with `allowManagedHooksOnly`, would keep the hook from running: the runner then refuses every sandboxed Claude Code start, reading them again at each start, and `check` names the file and the setting. A managed settings file the runner cannot read as JSON counts the same. Remove the setting to start agents again. On an ssh host the runner finds `maity` on the host's `agent_path` when it connects and starts the hook and the session loop by that absolute path; a host without `maity` there is refused.

Worktree isolation is not available to a placed Claude Code session: a registered worktree in the clone stops maity's git there, and the session cannot remove it from its sandbox. The runner configures this in the settings it writes for every Claude Code placement, sandboxed or not. They deny `EnterWorktree` by its bare name, which takes the tool out of the model's context, and `git worktree` from the shell (for opencode too), also over a repository grant that allows it. The deny does not match a global option before the subcommand (`git -C <dir> worktree …`): Claude Code still refuses such a line because no allow rule matches it, and opencode because its default is deny, unless a repository grant allows it; the start's prune and `maity runner check`'s warning cover a leftover. A deny of a name the binary does not know is taken as harmless, so both denies are in every file. For Claude Code 2.1.50 or later, the version the runner probed for the start, the settings also add a `WorktreeCreate` hook that prints no path and exits 2. Claude Code's hooks documentation names no version for that event; the 2.1.50 floor rests on Claude Code's v2.1.50 release notes, as cited in a review, and was not verified against a live binary. For an older or unknown version the runner writes no hook, and the two denies stand alone. By Claude Code's documentation the hook fails every worktree Claude Code would make: a subagent with `isolation: worktree`, a workflow agent's or a background session's, and `claude --worktree` started by hand. That behaviour was not confirmed on the hosted Claude Code version. Whenever the settings carry a hook, they also set `disableAllHooks` to `false`, over a `true` in the agents' user settings. In an unsandboxed placement that also turns on the agents' user's own hooks, which such a `true` had kept off. Settings that switch hooks off anyway leave only the two denies, sandboxed or not: a managed `disableAllHooks: true`, a managed `allowManagedHooksOnly`, or the agents' user's `allowManagedHooksOnly`. These are guards against an agent's mistakes, not a boundary.

`maity runner check` reports this configuration for each Claude Code host; it runs no live test. It warns instead where settings switch hooks off, or where the version is older than 2.1.50 or unknown: then only the denies apply. It also warns about a clone the runner recorded on that host that holds a worktree. A `.git/worktrees/` registration stops maity's git. The next start clears a registration whose working tree is under the clone's `.claude/worktrees/`. Any other registration stays until a person removes it outside the session (`git worktree remove` or `git worktree prune`). A bare directory under `.claude/worktrees/` with no registration does not stop maity's git, and the next start clears it; a file or a link there is not named, as it neither stops maity's git nor is removed by the start. Which of the two kinds a registration is, check tells only where it reads the clone as the runner's own user. Through sudo (the `agent_user` layout) or on an ssh host it names the registration without telling the kinds apart. A link as `.claude`, `.claude/worktrees`, `.git` or `.git/worktrees` counts as nothing found, as the start's prune clears nothing through a link. Check only reads; it removes nothing.

A Claude Code subagent's worktree-isolation, in a session a runner without that hook started, leaves a git worktree under the clone at `.claude/worktrees/`. A worktree there makes the clone read as not a plain clone, so `maity report` refuses with "Worktrees are not supported under the runner yet", and names the way out: stop and start the placement. On every placement (re)start the runner clears such a leftover worktree — before the clone check would refuse — by file operations only (it runs no git in an existing clone), returning the clone to a plain state so the session starts and `maity report` works again. It clears only a worktree whose working tree is a real directory directly under this clone's own `.claude/worktrees/`, reached without following a link at any step; a worktree that points anywhere else, and a link planted there, are left untouched, so a planted redirect still refuses the start and a person looks at it. There is no in-session remover: a restart's prune discards whatever is in the leftover worktree, including uncommitted work (a subagent's worktree is cleared only when the placement next starts, with no way to save from inside the session first), so commit or merge from a subagent's worktree before a restart if you need its work.

## Who agents commit as

Every agent the runner starts gets one default git identity, the same as author and committer, from the `[git]` table of the runner's configuration:

```toml
[git]
name = "Your Team"
email = "team@example.org"
```

Without `[git]`, agents commit as `Maity agent <maity-agent@invalid>`, a generic default that no forge links to anyone, and `maity runner check` warns until you set it. Use an identity for your agents, not a person's own: every agent of this runner commits under it.

The runner passes the identity to each session as `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME` and `GIT_COMMITTER_EMAIL`. These win over every git configuration, so a plain `git commit` works with nothing in `.git/config` and nothing in the agents' user's `~/.gitconfig`. In the `single` layout the agents' home is yours, and before this setting existed agents committed under the identity in your own `~/.gitconfig`; now they commit as `[git]`. What the runner guarantees is that default: every placed session starts with it as author and committer, and no git configuration replaces it (the clone's, the agents' user's, or one written later), because the variables win over configuration and `git config` and `git -c` are not granted. It is a default, not a lock: `git commit --author` gives a commit another author, and a program the session runs, such as an allowed check (see below), can start git with an environment of its own and commit under any identity. The name and the address take printable characters only (what Python's `str.isprintable()` accepts, so no control or format characters); a name has no `<` or `>` and no space at either end, an address exactly one `@` and no spaces. `check` and `serve` refuse anything else when they read the file. Placements that were already running get the identity only after a restart.

## Letting agents run a repository's checks

Besides `maity` and `git`, an agent may run only the commands its repository's grant lists. For a Python repository that runs pytest, Keep the Why's linter, black, ruff and mypy, add:

```toml
[repositories."github.com/you/demo"]
allow = [
  "python3 -m pytest *",
  "ktw-lint *",
  "black *",
  "ruff *",
  "mypy *",
]
```

- **End each entry with ` *`.** Claude Code applies an entry exactly as written: `pytest` alone allows only a bare `pytest`, and `pytest *` allows it with any arguments.
- **Name the check, not the interpreter.** `python3 -m pytest *` allows pytest; `python3 *` would allow any Python code.
- **The checks run the repository's code**, inside the harness's sandbox where it has one: tests, `conftest.py`, plugins. The allowlist is no boundary against that code (see [`maity runner`](../cli/README.md#maity-runner)).
- **Install the tools for the agents' user.** The sandbox reaches only the hub, the forge and the grant's `network` hosts, so an agent cannot install a missing tool itself.
- **Codex does not get the `allow` list.** Codex has no per-command allowlist, only its sandbox, so every command runs there, listed or not. With its sandbox on, a Codex placement still starts on a repository whose grant has an `allow` list or `pull_requests`; `maity runner check` and the runner's log at each start name what it does not get. With its sandbox off, such a grant refuses the start.

Each entry is a plain command; [`maity runner`](../cli/README.md#maity-runner) lists what is refused.

**A UUID source for Keep the Why.** Keep the Why gives every entry an `Id` made by a command, never typed by hand, and under the allowlist harnesses (Claude Code and opencode) the usual sources (`uuidgen`, `node`, `od /dev/urandom`, `cat /proc/sys/kernel/random/uuid`) are refused. The runner allows no UUID command of its own: an agent runs `maity uuid`, which is allowed wherever `maity` is, on every harness. `maity uuid` needs a `maity` from the release that ships it; with an older one (0.1.0a17 included) agents under Claude Code and opencode have no UUID source, so update `maity` on the runner and restart its placements. An earlier exact allow of `cat /proc/sys/kernel/random/uuid` never took effect in a placed Claude Code session (observed); the likely cause is that Claude Code checks a read command naming a path outside the working directories before it applies the allow rules (inferred), and opencode's `external_directory: deny` likely gates the same path (not observed in an opencode session).

## Clones after a stop

The hub keeps a retention time per placement (`workspace_retention`: `immediate`, `3h`, `24h` by default, `7d`), and the agent's owner or a project admin can ask for a kept clone to be removed (`POST /projects/<owner>/<slug>/placements/<id>/workspace/remove`). Removing clones when their time is up is the runner's part, and it is not built yet: today the runner keeps every clone until you remove it (`maity runner gc --revoked`).

## A placement's scratch

Reviews and tests leave things behind: evidence folders, a clone of another head, a virtual environment, temporary files. So each Claude Code or Codex placement gets a scratch directory beside its clone, `<workspaces>/<project_id>/.scratch/<placement id>`. The session finds it as `MAITY_SCRATCH`, with `TMPDIR` pointing inside it, and its sandbox may write there. `TMPDIR` points inside the scratch only when a Unix socket still fits under it: a socket path holds at most 107 bytes on Linux and 103 on macOS, and Claude Code's sandbox binds one there. Under the default `~/maity-workspaces` it usually does not fit, since any home longer than `/home/ab` leaves no room. A Codex or Claude Code placement on this machine then gets a short `TMPDIR` of its own: `<tmp>/maity-scratch-<uid>/<random leaf>/tmp`, in a 0700 leaf under the same per-user parent agy's scratch uses. Its sandbox, which hides that parent, opens this one leaf again for it alone, and the runner removes the leaf when the placement closes. The leaf is made fresh at every start, so temporary files do not survive a restart, and they do not count in the scratch's size. Claude Code's sandbox opens the leaf's `tmp`, so the commands it runs get a temporary directory of their own inside it. Claude Code's own temporary files and its sandbox's socket go in the leaf beside that `tmp` (`CLAUDE_CODE_TMPDIR`). Claude Code opens its own temporary directory there (`claude-<uid>/`) to the placement's commands itself: the directory is writable, its `tasks/` and `plugin-tool-staging/` are read-only, and only its socket directory stays hidden (checked live with 2.1.329). That stays within the placement, as it does wherever the scratch's own `tmp` is used, with one exception in the known gaps below. Where the leaf would not fit either (on macOS with a uid longer than four digits), and on an ssh host, the session gets no leaf either. A Codex session then starts without a `TMPDIR`. A sandboxed Claude Code placement is refused instead (`harness_refused`, with the cause in the runner's log), since its commands would otherwise share `/tmp/claude-<uid>` with every Claude Code session of that user. So on an ssh host, run sandboxed Claude Code placements under a short `workspaces` root. This holds for a Claude Code placement started after the runner was upgraded. Restarting the runner service is not enough: the runner adopts a session that is still running, and a supervised loop keeps the environment it was started with, so such a session keeps the shared temporary directory. After upgrading, restart each Claude Code placement (stop it and start it again). Set a short `workspaces` root, such as `/srv/mw`, to keep temporary files in the scratch itself. An agy placement gets a scratch too, so an agy reviewer can write its `review_result` file, but in a different place: its sandbox makes the beside-clone `.scratch` read-only, so the scratch goes under the host's shared temporary directory instead, in a per-user parent owned 0700 by the user the agents run as (`single`: the runner's user; `agent_user`: the agents' user). The session still finds it as `MAITY_SCRATCH`, with `TMPDIR` inside it. On an ssh host, whose remote user's id the runner does not hold, agy's placement gets none. opencode placements get none either, because the runner has not shown opencode's sandbox can write a scratch.

The agy scratch is created, read and removed with the care a shared temporary directory needs: the per-user parent and the per-placement directory are each made (or adopted only when already that user's own 0700 directory) without following a link, and the per-placement directory is made fresh at every start, so nothing carries across a restart and a directory planted by anyone else is refused rather than used. `maity say --review-file "$MAITY_SCRATCH/review.json"` is then read through the same path as any recorded scratch (an absolute path outside the clone, no link on the way); `repo/` stays read-only and the plain-call stdin rule for `maity` is unchanged.

The scratch is separated against other host users (the per-user parent and the per-placement directory are owned 0700 by the user agy runs as, so another host user cannot enter them) and against the sandboxed Codex and Claude Code placements of that same user, whose sandbox is told to hide the per-user parent so they cannot reach a scratch under it; the runner creates that parent before such a placement starts so the hidden path is a real directory. It is not separated against another agy placement, nor against an unsandboxed placement, of the same host user: a shared temporary directory is writable by that user and nothing here keeps one such placement out of another's scratch. The 0700 mode is ordinary own-user file permission and the per-placement name only keeps a user's placements from colliding; neither separates one same-user placement from another. That same-user exposure is accepted until each placement runs as its own user.

**agy is not a boundary between placements.** An agy placement's scratch can be read and written by every other agy placement of the same agents' user on that host. agy's deny rules are rules for its file tools; one test saw a read deny hide a directory from agy's sandboxed commands as well, but whether its rules keep commands out of a path in general, writes included, is not shown, and nothing in agy's settings denies paths to its commands at the OS level. The runner therefore gives agy no deny for the other scratches and does not claim one. The same holds for the other agy placements' sockets.

A Codex placement keeps its `CODEX_HOME` inside that scratch, so it lies under the workspaces root the codex sandbox opens for the placement and stays hidden from every other placement, rather than under the runner's state directory. The runner writes Codex's control files there once before the session starts, and the sandboxed commands may read the home but not write it. A Codex placement whose `CODEX_HOME` would instead fall under the state directory could run no command, so `maity resume` never started. `maity runner check` verifies, from the local configuration, the parts of this it can see before a placement starts — that Codex is given a scratch and that the workspaces root is not inside the state directory; it does not confirm that the scratch is actually created when a placement runs, nor check an ssh target's own paths, so a runtime fall-back to no scratch (where the home would again be hidden) is beyond what it catches. Without a scratch to carry it (no workspaces root to carve), `CODEX_HOME` stays in the runner's directory, where the sandbox hides it.

Nothing in a scratch counts as unsaved work. Once the hub reads the placement as closed and no session of it runs, the runner removes the scratch, writes a line to its log and adds the removal (when, which placement, path, size, why) to `removed.jsonl` in its state directory. A restart, a rejoin and an adoption keep it. Removing it after a stop, on the clone's retention clock, comes with the clone's removal (above), which is not built yet. The runner removes a scratch on a machine only after it has read that machine's agent sessions; while it cannot read them, every scratch there stays. It never makes or removes anything through a link: a link anywhere between the workspaces root and the scratch leaves the scratch as it is: no scratch is made through it (each start says why), and a removal it stops is logged once. On an ssh host, give `workspaces` as a path without a link on the way (the real path, for example `/var/home/...` where `/home` is a link): maity reads a file the agent names in its scratch only from `/` down without a link, so on such a path every read from the scratch is refused and the agent keeps its files in the clone. On the way down, maity only passes through each directory above the scratch and reads nothing from it. This is what makes the scratch work under Codex, whose sandbox hides the workspaces root and `.scratch` from reading while a path still leads through them. On Linux that takes only the right to search those directories. On macOS, which has no such open, maity still needs to read each of them.

- `maity runner status` shows the size of each placement's clone and scratch, measured at most every ten minutes. `maity runner status --removed` also shows the last removals.
- `maity runner gc --scratch` lists every scratch whose placement is no longer active. `--yes` removes them, and holds the service's lock, so stop the service first. gc asks the hub which placements are active: when it cannot ask, or one entry of the answer cannot be read, it removes nothing. It also reads the agents' sessions first and keeps the scratch of every placement that still has one, even a finished pane; when it cannot read them, it removes nothing.
- A runner whose own credential was revoked or removed cannot ask the hub any more, so gc cannot help there. Delete `<workspaces>/<project_id>/.scratch/` by hand, as you do its clones. After a revoke you can also pair the runner again: its closed placements are then no longer active, and `maity runner gc --scratch` finds their scratch.

Neither the sizes nor the removals go to the hub.

**Known gap:** the temporary directories above keep sandboxed placements apart, not unsandboxed ones. A placement without its sandbox reaches every file of its OS user, other placements' temporary files included. The `agent_user` layout does not keep placements apart, since it runs every agent of one runner as the same account. Only distinct OS accounts separate them here: separate runner targets, or runner instances that each run under their own OS user. And where the scratch's own `tmp` fits, a scratch made after a sibling Claude Code session started stays readable (not writable) from that sibling's sandbox, so in that start order the sibling can read the later placement's task output (tsk-07dwr3t80rg0). That Claude Code reads or runs nothing a placement's commands put in its own temporary directory was checked with no Claude Code plugins configured, and only on Claude Code 2.1.329; it is checked again when placements get plugins or the pinned version moves.

## Test slots and the test database in the scratch

A project's test scripts take a run slot for each heavy suite (`tools/run_slot.sh`) and keep a PostgreSQL test cluster (`hub/scripts/with_postgres.sh`). By default both live under `~/.local/state/maity/`, which no placement's sandbox may write. So the runner points both into the placement's scratch:

- `MAITY_RUN_SLOTS_DIR=<scratch>/slots`: the slot locks and the slot log.
- `MAITY_PG_DIR=<scratch>/pg` and `MAITY_PG_PASSWORD`: the test cluster, with its socket inside it (`with_postgres.sh` keeps its locks beside it, in `pg.locks`), and the password of its `postgres` role, so `with_postgres.sh` makes the cluster with `scram-sha-256` instead of `trust`.
  - **The password file:** the runner draws one password per placement and keeps it in a file of its own, 0600, under `<workspaces>/.maity-pg/`. That directory is 0700 and outside every scratch and clone. Claude Code's and Codex's sandboxes are denied it from the session's start, and agy's file tools are denied it too. opencode has no sandbox to deny it.
  - **How it reaches the session:** the session never reads the file. The runner starts the session through a small launcher, `pgenv`, which reads the password outside the sandbox and sets both variables in the session's process environment, so the password never appears on a command line, in tmux's environment or in a log.
  - **When the session gets neither:** the launcher sets both only when the password file is one the runner made and the socket path, `<scratch>/pg/.s.PGSQL.<port>`, fits a Unix socket path (107 bytes on Linux, 103 on macOS). Otherwise the session gets neither, and the runner's log says why. For the socket, set a shorter `workspaces` root. The password file goes when the placement closes.
  - **Not on ssh hosts yet:** the launcher is a module of the runner's own Python, not a `maity` command, so a placement on an ssh host gets no test cluster for now.
  - **Not in Claude Code placements yet:** on Linux, Claude Code's sandbox refuses Unix sockets, even inside the placement's own scratch, so the cluster cannot start there. macOS is untested, and the runner treats it the same. The runner draws no password file for a Claude Code placement and does not start it through the launcher. A test cluster over TCP for these placements is tsk-zk2cse7s2rf7. The test slots work in Claude Code placements as in the others.
  - **Codex:** a Codex placement gets the test cluster as described here, but no Codex session has started one yet.
- `MAITY_RUN_NAME=<handle>#<instance>`: who took a slot, as the log names it. It is the handle alone before the first join has named an instance.

This opens no path beyond the scratch, which the sandbox may already write. Everything in it stays with the placement and goes when the scratch goes. The sandboxes of Claude Code and Codex also keep a session out of every other placement's scratch. Claude Code gets each scratch that exists when the session starts in `denyRead` and `denyWrite`, the way it gets the other clones' credentials. A scratch made while a session runs is not covered for that session yet, a known residual tracked as tsk-rbys2j9q0m48: the session can read it, but cannot write it or connect to its test cluster, since Claude Code's sandbox refuses Unix sockets altogether. That last part holds only while the sandbox's seccomp step runs, which the runner checks for before every start ([Claude Code: Unix socket blocking](#claude-code-unix-socket-blocking)). Codex opens only the clone and its own scratch under the workspaces root, so it does not see the others. A start whose scratch listing cannot be completed is refused. agy and opencode are not kept out by these rules: neither is a boundary between placements of one OS user ([A placement's scratch](#a-placements-scratch), [OpenCode (Grok)](#opencode-grok)). Under these two harnesses the environment variables the runner sets are agent-settable too: a command the agent runs, `maity` included, can carry its own values for them. The slots bound only the runs of one placement. Bounding heavy runs across all the placements of a machine is a separate card (tsk-w7dx3h9mn8dp). A placement without a scratch beside its clone gets none of these variables, and its scripts use their defaults. That covers opencode, which has no scratch, and agy, whose scratch under `/tmp` is read-only to it except for its `tmp`.

## The Keep the Why skill

A project that uses Keep the Why asks every agent to load the skill and to confirm it with `maity ack keep-the-why`. A placed session cannot install the skill itself: its sandbox does not write the harness's skills directory, and it has no network for an installer. So the runner delivers the skill:

- **Which version:** the one the hub names on the placement (`keep_the_why`, `docs/api.md` §15.5). That is the release tree the resume packet names, plus the git commit of it (the hub's `MAITY_KTW_SKILL_COMMIT`). The runner fetches exactly that commit, never the tag, so a moved tag changes nothing it delivers.
- **Where it comes from:** the runner runs `git fetch` for that commit itself, outside any sandbox, over https only. **The runner's process needs to reach the source's host** (github.com by default); the session does not. The fetch takes the proxy and trust roots from the runner's environment (`HTTPS_PROXY`, `NO_PROXY` and their variants, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `GIT_SSL_CAINFO`, `GIT_SSL_CAPATH`), and no git configuration and no other `GIT_*` variable. A proxy set only in a git configuration is not used, so set it in the runner service's environment. Git checks every object against the commit id.
- **Where it goes:** `~/.local/share/maity-runner/skills/keep-the-why/<commit>-<source hash>/`, one copy per source and commit, beside the runner's state directory and not inside it. The runner takes only the skill's plain files: no links and no submodules, at most 200 files and 4 MiB. It writes them 0644 in 0755 directories and records each file's SHA-256 in a `manifest.json`. A copy is checked against that manifest at every start, for the source and commit it names too, within the same bounds, with every directory, the manifest and every file checked as what it should be and never followed through a link. The manifest's own SHA-256 is recorded in the runner's state directory (`skills.json`), which no session can reach, and a copy is handed out only with that manifest. Without a record (a new state directory), the runner fetches the commit again and keeps the copy only when it is the same. A copy that does not match is not handed out. Nothing in it is ever run. A source URL with a login in it (`user@`) is refused: the runner fetches without one.
- **Claude Code:** the copy is laid out as a Claude Code plugin, and the session starts with `--plugin-dir` for that copy, for that session only. Nothing is written into the agents' `~/.claude`. Claude Code names the plugin's skill `keep-the-why:keep-the-why`, and `maity resume` tells the agent to invoke it under that name. A plain `keep-the-why` the agents' user installed by hand still shows beside it, since the session reads the user's settings and skills; that copy may be another version, and the session cannot read its references. `maity runner check` warns when such a copy exists; it is yours, so the runner leaves it alone. The session's settings allow `Read` on the copy, so the agent can open the skill's references, which it otherwise could not read outside its clone and scratch. The copy is never writable from the session: an `Edit` deny and the sandbox's `denyWrite` hold it, and the Bash sandbox writes only the clone and the scratch anyway.
- **Every harness:** the session gets `MAITY_KTW_SKILL_DIR`, the directory with the skill's `SKILL.md`. `maity resume` then gives one way to load the skill in its Keep the Why block, in place of the hub's general texts: in Claude Code, the qualified name; for any other agent, that directory. The install lines are left out, since the skill is there.
- **When it cannot be had** (no network to the source, a commit the source does not have, a copy that does not match its manifest): the session starts without it. The runner's log says why, and the placement reports `keep_the_why_unavailable` with `running`. A missing sandbox (`sandbox_unavailable`) is reported first when both hold.
- **A new version** reaches a placement at its next start. A running session keeps the copy it started with.
- **Not yet:** the delivery works in the `single` layout on the runner's own host. In the `agent_user` layout the agents' user may not read the runner's directory, and an ssh host fetches for itself. Both start without the skill for now, with a log line, and report `keep_the_why_unavailable`. Codex gets only `MAITY_KTW_SKILL_DIR`, no skills directory of its own. `maity runner check` does not report the delivered skill yet (only a hand-installed copy), and `gc` keeps every cached commit. All of this is the next part of tsk-172s8y208whg.

## Keeping Claude Code and Codex current

The runner can install Claude Code and Codex and keep them current, per tool and only when you say so in its configuration:

```toml
[harness.codex]
install = true      # install it when it is missing (at start)
update = "daily"    # look for a newer version once a day, and on "Update now"
```

Without these lines nothing changes: the runner uses the tool it finds on the agents' PATH, and it reports no tools to the hub. With them it needs a hub that knows about managed tools (0.1.0a8 or later); an older hub refuses the runner at its start. With them it uses only its own copy, in `~/.local/share/maity-runner/tools/` of the runner's user, never one on the PATH; a `binary` setting for such a tool is refused. A newer version goes in beside the one in use and is used from the next start of a session, never under a running one; the version before stays, and `maity runner tools rollback codex` goes back to it (a second rollback goes forward again; while an install or update of the tool runs, it is refused, try again after it). Older versions are removed once no running session uses them. With `install = false`, a missing tool is not installed by an update either. `maity runner tools` lists what is installed. The owner can ask for an update at once ("Update now", above; the dashboard has no button for it yet); the runner reads it within a minute.

What the runner checks before it uses a download, and what it does not:

- **Claude Code:** the exact version from Anthropic's download server, its release manifest signed by Anthropic's release key (shipped inside `maity`, fingerprint `31DD DE24 DDFA B679 F42D 7BD2 BAA9 29FF 1A7E CACE`), the binary matching the manifest's SHA-256 and size. It needs `gpgv` on the machine (`gpgv` or `gnupg` package); without it the install is refused.
- **Codex:** the exact release from OpenAI's GitHub repository, its package matching the SHA-256 GitHub states for it. The release's sigstore signature is not checked.
- No vendor install script is ever run, and nothing falls back to an unchecked download: a failed check reports `failed` (`installer_failed`) and keeps the version in use.

The runner never logs a tool in. After an install, log in to it once as the agents' user, as the tool's own documentation says; until then the tool is reported `login_needed` and offered to no placement; the runner checks once a minute and offers it again as soon as you have logged in. A managed tool does not update itself (the runner switches its own updater off), and the runner manages tools only on its own machine: not on an ssh target, and not yet in the `agent_user` layout. Updating `maity` itself this way is not built yet.

## Logs and a full disk

The runner's own log is one line per event on its standard error: the terminal of `maity runner serve`, or under the `maity-runner.service` unit the journal (`journalctl -u maity-runner`). A refused join writes a warning there that names what the dashboard does not show. A refused pickup gives `<placement>: warning: join pickup refused: <code> (reason <reason>, why <why>)`. For `pickup_not_allowed`, `why` holds the cause: `not_running`, `stale_generation`, `credential_issued`, `project_not_allowed`, `handle_taken` or `creator_lacks_authority` ([`docs/api.md` §15.9](api.md#159-the-join-pickup)). The placement itself reports only `join_failed` with the code. A refused exchange gives `<placement>: warning: join exchange refused: <code> (reason -, why -)`, because the exchange answers `not_found` without a why. A value that is not in the form of a code is shown as `-`, and the join's URL and code are never logged.

Each placement's session output goes to a log on the runner, which `maity runner logs <agent>` shows. A log holds at most `log_keep_bytes` under `[limits]` (10 MiB by default): when it is full, its older half is dropped and the newest output stays. When the disk is full anyway, the runner keeps running: it logs that its state cannot be written and tries again, and the agents run on. Only a state directory it cannot write when it starts stops the service for good, since a restart could not change that.

## Working in an agent's clone

An agent's clone on the runner belongs to the agent. You look there, you don't work there.

- Read the work from the pushed branch or the pull request.
- To look inside the clone, run git there only when it passed the runner's check and no session ran since. The runner checks each clone before it starts an agent in it, so that holds only when the clone passed and the start stopped before a session (the join failed, for example, or the placement was stopped meanwhile), or when `maity runner gc --revoked` passed it: gc checks only a clone whose credential is revoked and that no placement uses, and lists one that fails as `not inspected`. A clone the check refused (`not_a_plain_clone` at a start, `not inspected` in gc's list) never qualifies: do not run git in it at all. While an agent runs there, read the pushed branch instead.
- In a checked clone, use only git that reads: `git log`, `git diff`, `git show`. Unchecked, a clone's own configuration can make even `git diff` run a program the agent put there.
- Never continue what the agent left: no `git rebase --continue` or `--skip`, no `git cherry-pick --continue` or `git am --continue`. The agent can write those states; an `exec` line it planted in a rebase's todo list would run as you.
- Do your own work in a clone of your own.

The check covers the clone as it was then, and a session can change it afterwards. [`maity runner`](../cli/README.md#maity-runner) has the details.
